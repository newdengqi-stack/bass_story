## 1. 适用范围

本规范用于 Web 平台数据库的表设计、字段设计、约束、索引、SQL、事务、迁移、数据访问、备份、恢复、权限、审计、性能以及 AI Coding Agent 修改数据库相关代码时的行为。

示例优先使用 PostgreSQL；规则可迁移到 MySQL 等关系型数据库，但具体 DDL 需结合实际数据库能力。

规则类型：

- **【安全红线】**：绝不允许违反。
- **【强制规则】**：项目/企业工程规范，必须执行。
- **【条件强制】**：满足场景时必须执行。
- **【建议】**：正常情况下应遵循。
- **【说明】**：解释。
- **【示例】**：正确/错误示例。
- **【例外】**：必须显式记录原因。

## 2. 数据库总体原则

```text
数据正确性
  ↓
数据安全
  ↓
一致性
  ↓
可恢复性
  ↓
可维护性
  ↓
性能
```

核心原则：

> 能由数据库保证的数据约束，优先由数据库约束保证，而不是只依赖后端代码。

PostgreSQL 提供 NOT NULL、UNIQUE、PRIMARY KEY、FOREIGN KEY、CHECK 等约束机制，应合理使用。citeturn684376search0

## 3. 数据库架构

推荐：

```text
Frontend
   ↓
Backend API
   ↓
Service
   ↓
Repository / DAO
   ↓
Database
```

- 【强制规则】浏览器不得直接连接生产数据库。
- 【安全红线】数据库凭据不得进入前端。
- 【强制规则】数据库访问必须经过后端或明确的受控服务层。
- 【强制规则】生产数据库不向公网直接暴露。

---

## 4. 命名规范

- 【强制规则】表名、列名、索引名、约束名统一使用 `snake_case`。
- 【强制规则】命名必须统一采用项目既定的单数/复数策略。
- 【强制规则】禁止同一项目混用 `userInfo`、`user_info`、`UserInfo`。
- 【强制规则】表名和列名必须表达业务语义，禁止大量 `data1`、`tmp1` 等无意义名称。
- 【建议】约束和索引名称包含表/字段语义。

示例：

```text
users
user_profiles
orders
order_items
idx_orders_user_id
uq_users_email
fk_order_items_order_id
```

---

## 5. 主键规范

- 【强制规则】业务实体必须具有稳定主键。
- 【强制规则】主键不得使用容易改变的业务字段。
- 【建议】使用 UUID、BIGINT Identity 等稳定方案。
- 【安全/工程规则】对外暴露 ID 时必须结合授权检查，不能认为“ID 难猜”就是权限控制。

---

## 6. NOT NULL

- 【强制规则】业务上必填字段必须使用 `NOT NULL`。
- 【强制规则】不得仅靠前端验证保证数据库不出现 NULL。
- 【条件强制】允许为空必须有明确业务语义。

例如：

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username VARCHAR(64) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL
);
```

---

## 7. UNIQUE

- 【强制规则】业务上必须唯一的数据必须使用数据库唯一约束或唯一索引。
- 【安全红线】不能只通过“先查询再插入”保证唯一性。

错误思路：

```text
SELECT 检查邮箱不存在
    ↓
INSERT 用户
```

并发请求可能同时通过检查。

正确思路：

```text
数据库 UNIQUE
        +
事务/错误处理
```

---

## 8. CHECK

- 【强制规则】数据库能够直接表达且必须保证的数值范围、状态范围，应考虑 `CHECK` 约束。

例如：

```sql
price NUMERIC(12, 2) CHECK (price >= 0)
```

- 【说明】CHECK 用于数据层的基本合法性保证；复杂业务规则仍应放在 Service 层。

---

## 9. 外键

- 【强制规则】存在真实实体关联时优先使用 FOREIGN KEY。
- 【强制规则】外键的删除/更新策略必须根据业务明确选择。
- 【强制规则】禁止无理由使用 `CASCADE`，必须评估级联删除影响。
- 【建议】外键列根据实际查询/维护路径考虑索引。

PostgreSQL 官方文档说明外键保证引用完整性，而引用列不一定会自动获得索引，因此引用侧通常需要结合查询和删除/更新行为单独评估索引。citeturn684376search0

---

## 10. 时间字段

- 【强制规则】创建时间、更新时间等字段必须统一命名。
- 【强制规则】时间字段必须明确时区语义。
- 【建议】Web 平台统一使用 UTC 存储，在展示层转换用户时区。
- 【强制规则】不得在数据库中混乱使用本地时间和 UTC 时间而无字段语义说明。

---

## 11. 金额与精度

- 【安全红线】金额等精确数值不得使用普通浮点类型存储。
- 【强制规则】明确币种、精度和舍入规则。
- 【建议】金额使用 NUMERIC/DECIMAL 或以最小货币单位整数存储，具体方案必须项目统一。

---

## 12. 状态字段

- 【强制规则】状态值必须有明确集合。
- 【强制规则】不得在业务代码中散落大量魔术字符串。
- 【建议】状态变化设计为明确状态机。
- 【条件强制】状态转换有顺序要求时，数据库和 Service 必须共同保证非法跳转无法发生。

---

## 13. 软删除

- 【条件强制】需要保留历史数据的业务实体可以使用软删除。
- 【强制规则】软删除字段必须统一，例如 `deleted_at`。
- 【强制规则】所有正常查询必须明确是否过滤软删除数据。
- 【强制规则】不能因为存在软删除字段就忽略唯一性设计。

---

## 14. SQL 注入

- 【安全红线】禁止字符串拼接 SQL。
- 【强制规则】使用参数化查询/ORM 参数绑定。
- 【安全红线】用户可控排序字段、列名、表名不能直接拼接进入 SQL。
- 【强制规则】动态结构只能使用 allow-list 映射。

OWASP 明确建议使用参数化查询，避免把用户输入作为 SQL 代码的一部分。citeturn644693search0turn644693search1

错误：

```python
sql = f"SELECT * FROM users WHERE username = '{username}'"
```

---

## 15. SELECT * 规则

- 【强制规则】业务查询禁止无理由使用 `SELECT *`。
- 【强制规则】API 查询应只获取实际需要的字段。
- 【建议】减少不必要数据传输和 ORM 对象构造。

允许的例外：

- 临时诊断；
- 管理员离线分析；
- 明确无需字段控制的内部查询。

---

## 16. 查询分页

- 【强制规则】面向用户的列表查询必须分页、限制数量或采用明确的游标策略。
- 【安全红线】不得允许客户端传入任意超大 limit。
- 【强制规则】必须有最大 page size。
- 【建议】大数据量场景优先考虑 keyset/cursor pagination。

---

## 17. 索引

- 【强制规则】高频查询条件必须评估索引。
- 【强制规则】唯一性要求使用 UNIQUE/唯一索引。
- 【建议】根据真实查询计划调整索引。
- 【强制规则】禁止为了“感觉快”给每个字段都建索引。
- 【强制规则】新增索引必须评估写入成本和存储成本。

PostgreSQL 官方文档强调索引可以显著提高读取速度，但也会带来额外系统开销，应根据真实工作负载合理使用，并可用 EXPLAIN 等方式检查使用情况。citeturn913701search0turn913701search10

---

## 18. 复合索引

- 【强制规则】多条件高频查询应根据 WHERE、ORDER BY 和 JOIN 条件设计复合索引。
- 【建议】索引列顺序必须结合实际查询模式设计。
- 【强制规则】不得只因为“字段都常用”就随意组合索引。

---

## 19. 事务

- 【安全红线】必须原子完成的多步数据库操作必须放在同一事务中。
- 【强制规则】事务边界通常由 Service/业务操作确定。
- 【强制规则】事务不要包含不必要的网络请求或长时间计算。
- 【条件强制】竞争更新必须明确并发控制策略。

PostgreSQL 支持 Read Committed、Repeatable Read、Serializable 等隔离级别，Serializable 下应用需要处理 serialization failure。citeturn913701search3turn913701search5

---

## 20. 并发一致性

- 【安全红线】库存、余额、配额等不能出现竞态条件。
- 【强制规则】不能使用“先 SELECT，再 UPDATE”作为唯一并发保护。
- 【建议】根据业务使用事务锁、条件 UPDATE、乐观锁或 Serializable。

错误：

```text
SELECT stock
  ↓
Python 判断 stock > 0
  ↓
UPDATE stock = stock - 1
```

两个并发请求可能同时通过判断。

应考虑原子条件更新或正确的事务锁策略。

---

## 21. Migration 规则

- 【强制规则】数据库结构修改必须通过 Migration 管理。
- 【强制规则】生产环境禁止手工随意执行未记录 DDL。
- 【强制规则】Migration 必须可追踪、可审查。
- 【强制规则】Migration 必须考虑旧版本应用兼容。
- 【条件强制】破坏性变更采用分阶段迁移：先加新字段/兼容逻辑，再迁移数据，再删除旧字段。
- 【安全红线】不得在 Migration 中无条件删除生产数据。

---

## 22. 数据迁移安全

- 【强制规则】大规模数据迁移必须评估锁、IO、事务时长和业务影响。
- 【建议】将大任务拆分为可恢复的小批次。
- 【强制规则】迁移失败必须能够定位失败阶段。
- 【条件强制】生产迁移前必须完成备份和恢复验证。

---

## 23. 数据库权限

- 【安全红线】应用账号不得使用不必要的超级用户权限。
- 【强制规则】不同环境使用不同数据库账号。
- 【条件强制】读写分离时使用不同角色/账号。
- 【强制规则】生产凭据存放在 Secret 管理系统中。

---

## 24. 敏感数据

- 【安全红线】密码不得明文存储。
- 【安全红线】Token、私钥等秘密不得以普通业务字段随意落库。
- 【强制规则】敏感数据确需持久化时必须明确加密、密钥管理、访问控制和审计策略。
- 【强制规则】备份中的敏感数据同样需要保护。

密码应该使用 Argon2id 等慢速、带 salt 的密码哈希，而不是可逆加密或快速哈希。citeturn644693search4

---

## 25. 审计字段

对需要追踪的数据表，可统一考虑：

```text
created_at
updated_at
created_by
updated_by
deleted_at
```

- 【强制规则】审计字段含义必须统一。
- 【条件强制】关键管理操作需要独立审计日志，不应只依赖业务表的 `updated_at`。

---

## 26. 数据库错误处理

- 【强制规则】数据库异常不能直接把 SQL、连接串、内部结构返回给用户。
- 【强制规则】唯一约束、外键约束、CHECK 等异常必须转换为明确业务错误或统一错误码。
- 【安全红线】不得因为“方便开发”把原始数据库异常直接返回前端。

---

## 27. 备份与恢复

- 【安全红线】生产数据库必须具备明确备份策略。
- 【强制规则】备份必须定期验证可恢复性。
- 【强制规则】备份与生产数据库不能只有单一存储位置。
- 【条件强制】重要系统根据 RPO/RTO 设计持续归档或 Point-in-Time Recovery。
- 【强制规则】恢复演练必须留有记录。

PostgreSQL 官方文档提供 SQL Dump、文件级备份和连续归档/PITR 等方案，并强调数据库应定期备份。citeturn913701search2

---

## 28. 性能与 EXPLAIN

- 【强制规则】出现明显慢查询时必须检查执行计划，而不是只凭感觉加索引。
- 【建议】使用 EXPLAIN/EXPLAIN ANALYZE 评估复杂查询。
- 【强制规则】禁止通过无限增加索引解决所有性能问题。
- 【条件强制】大表迁移、删除、更新必须评估执行计划与锁影响。

---

## 29. 数据访问层

- 【强制规则】数据库访问统一从 Repository/DAO 或项目规定的数据访问层进入。
- 【强制规则】Controller 不直接执行 SQL。
- 【强制规则】Service 负责业务事务边界。
- 【强制规则】Repository 不应包含复杂权限业务。

---

## 30. AI Coding Agent 规则

### 修改数据库结构之前

AI 必须先分析：

```text
现有表
字段
主键
外键
唯一约束
索引
数据量
调用方
Migration 历史
兼容版本
```

### 修改中

- 【强制规则】必须通过 Migration 修改数据库结构。
- 【安全红线】不得擅自删除字段、表、索引或历史数据。
- 【强制规则】新增字段必须考虑默认值、NULL、旧代码兼容。
- 【强制规则】新增索引必须分析查询场景。
- 【强制规则】修改唯一约束必须分析并发和旧数据。
- 【强制规则】修改外键必须分析删除/更新行为。

### 修改后

```text
[ ] Migration 可追踪
[ ] 旧版本兼容性已检查
[ ] 主键/外键正常
[ ] UNIQUE/NOT NULL/CHECK 正常
[ ] 索引合理
[ ] SQL 参数化
```
