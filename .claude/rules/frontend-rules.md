## 1. 适用范围

本规范用于 Web 前端项目的页面、组件、状态管理、网络请求、表单、路由、样式、类型、可访问性、性能、安全以及 AI 生成/修改代码。

规则结构：

- **【安全红线】**：涉及浏览器安全、用户数据、认证凭据、XSS、CSRF、敏感信息和供应链风险，禁止违反。
- **【强制规则】**：项目/企业工程规范，必须执行；即使不是框架或语言本身的要求，也不能自行忽略。
- **【条件强制】**：满足条件时必须执行。
- **【建议】**：正常情况下应遵循，特殊场景需说明原因。
- **【说明】**：解释规则原因。
- **【示例】**：展示正确或错误用法。
- **【例外】**：明确特殊情况和审批要求。

---

## 2. 规则优先级

```text
安全红线
  ↓
数据与用户行为正确性
  ↓
接口契约与状态一致性
  ↓
项目强制工程规则
  ↓
条件强制规则
  ↓
性能优化
  ↓
普通建议
```

企业工程规则不是“可选建议”。例如组件行数、文件结构、TypeScript 类型、API 调用边界等均属于本项目强制要求。

---

## 3. 技术栈约定

本规范保持框架相对独立；示例优先使用 TypeScript + React/Vite 表达。若实际使用 Vue、Svelte、Next.js 等，应保持相同工程原则，仅替换对应语法。

- 【强制规则】前端必须启用 TypeScript 严格类型检查；禁止以 `any` 作为逃避类型问题的常规手段。
- 【强制规则】页面、组件、服务、类型、状态等职责必须分层。
- 【强制规则】不得在 UI 组件中堆积网络请求、复杂业务规则和数据库语义。
- 【强制规则】API 类型与后端契约必须保持一致。

---

## 4. 项目目录

推荐结构：

```text
src/
├── api/            # API 请求层
├── components/     # 通用 UI 组件
├── pages/          # 页面
├── layouts/        # 页面布局
├── hooks/          # 通用 Hooks
├── stores/         # 全局状态
├── types/          # 类型定义
├── utils/          # 无业务状态的工具
├── constants/      # 常量
├── assets/         # 静态资源
├── router/         # 路由
└── styles/         # 全局样式/主题
```

- 【强制规则】业务 API 不直接散落在页面组件中。
- 【强制规则】通用组件不得依赖具体业务页面。
- 【强制规则】工具函数不得偷偷持有全局业务状态。
- 【强制规则】目录职责清晰，不得为了少建文件把所有代码塞进单个文件。

---

## 5. 文件与组件规模

这是企业级项目的强制工程规则。

- 【强制规则】单个 `.ts/.tsx` 文件原则上不超过 **400 行**，不含大段纯类型生成代码和机器生成文件。
- 【强制规则】单个 React 组件原则上不超过 **250 行**。
- 【强制规则】单个函数原则上不超过 **60 行**。
- 【条件强制】超过限制时必须检查是否可以按职责拆分。
- 【强制规则】禁止通过删除空行、压缩代码或隐藏逻辑规避行数限制。
- 【强制规则】不得为了“拆文件”制造只有几行且没有独立职责的伪组件。

示例：页面同时包含数据请求、复杂过滤、表格、弹窗和表单时，应拆成页面容器 + 数据 Hook + 表格组件 + 表单组件，而不是继续堆在一个文件中。

---

## 6. TypeScript 类型规则

- 【强制规则】业务数据必须具有明确类型。
- 【强制规则】禁止使用 `any` 逃避接口契约。
- 【强制规则】外部数据必须经过类型校验后才能进入业务逻辑。
- 【强制规则】可空字段必须显式表示，例如 `string | null`。
- 【强制规则】枚举状态优先使用 union type、enum 或后端统一的状态常量。
- 【强制规则】不得把 API 返回值无条件断言成正确类型。

错误：

```ts
const data = response.data as User;
```

更可靠：先验证返回结构，再进入业务层。

---

## 7. 组件设计

- 【强制规则】组件职责单一。
- 【强制规则】通用组件不得耦合具体页面业务。
- 【强制规则】Props 必须有明确类型。
- 【强制规则】复杂状态优先通过 Hook、store 或专用状态模块管理。
- 【建议】优先组合组件，而不是创建巨型组件。
- 【强制规则】不得通过大量 boolean props 制造难以维护的组件状态组合。

---

## 8. 状态管理

- 【强制规则】服务器状态与本地 UI 状态必须区分。
- 【强制规则】不得把所有 API 数据无理由复制到全局 store。
- 【强制规则】全局状态只保存真正跨页面共享的数据。
- 【强制规则】敏感认证凭据不得放入普通全局状态后再持久化到浏览器存储。
- 【条件强制】复杂异步状态必须明确 loading、success、empty、error 等状态。

---

## 9. API 请求层

- 【强制规则】所有后端请求必须通过统一 API 层或统一 HTTP Client。
- 【强制规则】不得在几十个组件中重复实现请求、错误解析和鉴权逻辑。
- 【强制规则】请求参数、响应数据、错误响应必须有明确类型。
- 【强制规则】统一处理超时、取消、认证失效、网络错误和业务错误。
- 【强制规则】不得在前端复制一份后端的核心权限判断作为唯一安全措施。

说明：前端权限控制只负责 UI 展示和交互体验，最终授权必须由后端再次验证。OWASP API Security Top 10 将对象级和功能级授权失效列为核心 API 风险。citeturn340065search1turn340065search8

## 10. 认证凭据与浏览器存储

- 【安全红线】禁止将登录 Token、Session ID、Refresh Token 或其他认证凭据长期存储于 `localStorage` 或 `sessionStorage`。
- 【强制规则】优先使用 `HttpOnly + Secure + SameSite` Cookie 或 BFF 方案保存浏览器会话。
- 【强制规则】Cookie 必须设置合理的过期时间、Path 和 SameSite 策略。
- 【条件强制】使用 Cookie 承载认证时，所有状态改变请求必须具备 CSRF 防护。

OWASP 明确警告不要把认证凭据放进 Web Storage，因为 XSS 可直接读取；其会话管理建议包括 `HttpOnly`、`Secure` 和明确的 `SameSite`。citeturn913701search12turn644693search6

---

## 11. XSS 安全

- 【安全红线】禁止将未经可信验证和消毒的 HTML 直接插入页面。
- 【安全红线】React 中禁止滥用 `dangerouslySetInnerHTML`。
- 【条件强制】Markdown/富文本渲染必须使用经过维护并完成安全过滤的解析链。
- 【强制规则】用户输入默认视为不可信数据。
- 【建议】部署 CSP 作为纵深防御。

React 官方明确指出，未经信任或清洗的内容使用 `dangerouslySetInnerHTML` 会导致 XSS 风险；OWASP 将 CSP 作为 XSS 等客户端攻击的纵深防御手段。citeturn684376search5turn644693search3

错误：

```tsx
<div dangerouslySetInnerHTML={{ __html: userInput }} />
```

只有在内容来源可信且经过严格清洗时才允许使用。

---

## 12. CORS 与跨域

- 【强制规则】前端不得假设 CORS 是由前端代码决定的；CORS 由服务端响应头控制。
- 【强制规则】生产环境不得默认接受任意 Origin。
- 【条件强制】使用 Cookie/凭据跨域时必须显式配置允许的 Origin，不得使用 `*` 与凭据模式组合。
- 【建议】开发环境与生产环境分别维护允许 Origin 配置。

FastAPI 官方文档明确说明 Origin 由协议、域名和端口组成，带凭据的 CORS 配置需要显式指定允许的 Origin。citeturn684376search1

---

## 13. 表单与输入校验

- 【强制规则】所有用户输入必须进行前端校验。
- 【安全红线】前端校验不得代替后端校验。
- 【强制规则】输入框明确最大长度、最小长度、格式和允许字符。
- 【强制规则】提交按钮必须处理重复点击。
- 【条件强制】文件上传必须校验大小、扩展名、MIME 类型并显示上传状态。
- 【建议】错误提示靠近对应控件，并保持可访问性。

---

## 14. 用户体验状态

页面必须考虑：

```text
loading
success
empty
error
partial success
permission denied
network unavailable
session expired
```

- 【强制规则】不得出现 API 失败后页面无限 loading。
- 【强制规则】空数据必须有明确 empty 状态。
- 【强制规则】权限不足必须与系统错误区分。
- 【条件强制】写操作必须防止重复提交，并在需要时支持幂等请求。

---

## 15. 路由与权限

- 【强制规则】路由权限只负责前端体验，不作为真正安全边界。
- 【强制规则】登录页、公共页、受保护页必须明确分类。
- 【强制规则】认证失效后统一处理跳转/重新认证。
- 【安全红线】不得仅依靠隐藏按钮保护敏感操作。

---

## 16. 网络错误与超时

- 【强制规则】请求必须具备超时策略。
- 【强制规则】组件卸载或请求失效时，长请求应能够取消。
- 【强制规则】网络错误不能直接把底层堆栈展示给用户。
- 【强制规则】敏感错误详情只能进入受控日志系统。

---

## 17. 性能规则

- 【强制规则】禁止无意义的大体积依赖。
- 【建议】长列表使用虚拟列表或分页。
- 【建议】图片使用合适尺寸、格式和懒加载。
- 【建议】避免不必要的全局状态导致大面积重新渲染。
- 【建议】页面首次加载关键资源优先加载。
- 【条件强制】大数据表格必须进行分页、虚拟化或服务端查询。

---

## 18. 可访问性

- 【强制规则】可交互元素必须可通过键盘操作。
- 【强制规则】图片和图标在需要语义时提供可访问名称。
- 【强制规则】表单控件必须具有明确 label。
- 【建议】遵循 WCAG 的基本可访问性原则。
- 【强制规则】不得仅依赖颜色表达错误、成功或状态。

---

## 19. 环境变量和敏感信息

- 【安全红线】不得把数据库密码、JWT 私钥、第三方 Secret、内部 API Key 写入前端代码。
- 【安全红线】前端构建产物中的环境变量默认视为公开信息。
- 【强制规则】只能把真正允许公开的配置暴露给浏览器。
- 【强制规则】敏感配置必须存放于后端或部署环境的 Secret 系统。

---

## 20. 第三方依赖

- 【强制规则】引入依赖前必须确认维护状态、许可证和安全风险。
- 【安全红线】禁止从陌生 CDN 动态执行未知脚本。
- 【建议】锁定依赖版本并定期进行依赖安全扫描。
- 【条件强制】使用 CDN 脚本时应采用 Subresource Integrity 等机制。

---

## 21. AI Coding Agent 规则

### 修改前

- 【强制规则】先读取现有目录、路由、组件和 API 层。
- 【强制规则】确认使用的前端框架、构建工具和状态管理方案。
- 【强制规则】不得因为任务简单就绕过项目已有组件和 API 层。

### 修改中

- 【强制规则】最小修改。
- 【强制规则】禁止无关重构。
- 【强制规则】禁止擅自替换 UI 库。
- 【强制规则】禁止擅自修改 API 契约。
- 【强制规则】禁止使用 `any` 掩盖类型问题。
- 【安全红线】禁止为了“页面能显示”绕过鉴权、校验或错误处理。

### 修改后

必须检查：

```text
[ ] TypeScript 类型检查通过
[ ] API 类型与后端契约一致
[ ] 无新增 any
[ ] 无 XSS 风险
[ ] 无敏感信息进入前端
[ ] 无 localStorage 保存认证凭据
[ ] 无无限 loading
[ ] loading/empty/error 状态完整
[ ] 组件/文件行数符合限制
[ ] 无无关修改
[ ] 构建通过
```
