## Context

动机见 `proposal.md - Why`。这里只记录影响实现方式的现状与约束。

### 现有设计系统（实测自 `luod/`，新页面必须沿用）

**技术栈**：Next.js 16（App Router）+ React 19 + Tailwind CSS v4 + shadcn 目录结构（`components.json`）。样式以 Tailwind 原子类为主，主题变量集中在 `app/globals.css`。无状态管理库、无图表库、无 UI 组件库运行时依赖。

**色彩**——应用内页面用 `.ws` 作用域，是一套「照片上的文字」体系：

| Token | 值 | 用途 |
|---|---|---|
| `--ws-ink` | `#fbf9f6` | 主文字（白） |
| `--ws-ink-2` | `#e4ded6` | 次级文字 |
| `--ws-muted` | `#b5aca0` | 辅助文字 |
| `--ws-line` / `--ws-line-2` | 白 20% / 34% | 分隔线、次要线条 |
| `--ws-sand` / `--ws-sand-fill` | `#e9c9a8` | 品牌强调色；填充态配 `#2a2140` 深紫字 |
| `--ws-ghost` / `--ws-ghost-hover` / `--ws-ghost-line` | 白 10% / 20% / 24% | 幽灵控件 |
| `--ws-ok` / `--ws-info` / `--ws-warn` / `--ws-miss` | `#86efac` / `#93c5fd` / `#fcd34d` / `#fda4af` | 四种证据状态的语义色 |

**排版**：`--font-sans` = Noto Sans SC（正文、界面）；`--font-serif` = Noto Serif SC（仅落地页品牌字）。字号直接用 Tailwind 任意值（`text-[13px]`、`text-[26px]`、`text-[3.75rem]`），未定义字号阶梯。正文行高 1.6–1.7。

**字色可读性机制**：`.ws` 在容器上设了双层 `text-shadow`（`0 1px 3px rgb(12 9 20/.75), 0 2px 16px rgb(12 9 20/.45)`），投影只作用于文字、不作用于背景图——这是当前页面能在照片上保持可读的唯一手段，**不得移除**。

**圆角**：胶囊用 `rounded-full`；方块容器用 `1rem`（`.ws-ghost-box`）；历史卡片层用 `1.125rem`。shadcn 的 `--radius: 0.625rem` 及其派生值未被应用页使用。

**阴影**：应用页**刻意不用投影**（照片上投影会产生脏光晕），深度只靠字重、字号与留白。落地页除外。

**间距**：无 token，直接使用 Tailwind 的 4pt 系列（`gap-2/3/4/6/8`、`py-5/6/20/28`）。

**动效**：`fade-up`（0.9s，`cubic-bezier(.22,1,.36,1)`）、`.reveal`（IntersectionObserver 触发一次）、以及点阵用的环境动效（`breathe` / `ring-pulse` / `spin-slow` / `wave-flow` / `scan-x` / `dot-hop` / `draw-check`）。全部在 `prefers-reduced-motion` 下降级为静态。

### 已知问题（本次**不**擅自重构，仅记录）

1. `app/globals.css` 顶部的 shadcn `:root` / `.dark` 灰阶 token 与 `.ws` 体系并存且互不影响，属于脚手架残留。应用页实际不消费它们。
2. `components/ui/button.tsx` 从未被任何页面引用。
3. 字号没有阶梯，同一层级在不同页面可能出现 `text-[17px]` 与 `text-[18px]` 两种取值。

以上三项都在本次改动范围之外——按「不为了新页面破坏已有约定」的原则，先记录，不处理。

## Goals / Non-Goals

**Goals:**

- 11 个新页面在视觉上与现有 4 个页面**被认作同一产品**：切换页面时不应感到换了套设计
- 把 6 个全局组件抽成可复用件，让后续页面不必再各写一遍
- 把两条业务硬规则**落到组件层**，使其无法被某一页绕过：来源必须可回链、无来源不可操作
- 保持无后端前提，全部页面可在本地跑通并能演示完整闭环

**Non-Goals:**

- 不重新设计视觉语言，不引入新的色彩、字体、圆角或阴影体系
- 不接入后端、不做真实认证与持久化（沿用现有本地 mock 模式）
- 不实现 P1 页面（面试复盘、模拟训练、资源库、多岗位管理）
- 不修复上文记录的 3 项既有问题
- 不引入新的第三方依赖

## Decisions

### D1 · 新页面是现有原子件的新组合，而不是新体系

**选择**：每个新页面 = `AppShell`（照片背景 + 导航）+ `.ws*` token + `PixelGlyph/BitRegister/PixelRule` 点阵件 + 手写 Tailwind 原子类的组合。

**理由**：一致性来自复用同一批原子件。上一轮迭代已经确立了「内容直接落在照片上、没有卡片、靠文字投影可读」的形态，新页面若重新引入卡片或遮罩，会立刻显得是另一个产品。

**替代方案**：为信息密集页面（如追问会话）单独引入玻璃卡片提高可读性。**否决**——已在上一轮验证过：遮罩会让照片发灰，卡片会破坏「无容器」的统一形态。

**替代方案**：为每个新页面单独设计布局语言。**否决**——这正是本变更要避免的结果。

### D2 · 六个全局组件抽取到 `components/shared/`

**选择**：新建 `components/shared/`，落地规格 §2.2 列出的六个全局组件：证据状态标签、来源浮层、步骤指示器、任务卡、空态块、逐条确认操作条。

**理由**：这六个东西在 11 个页面里反复出现。不抽的话每页各写一遍，必然出现同一状态在两页显示不同颜色、同一空态在两页文案结构不同——这是「看起来像两个产品」最常见的成因。

**替代方案**：继续在页面内联实现。**否决**——规格 §2.1 已经把这些定为强制性全局约定，实现层必须与之对应。

### D3 · 证据门禁放在组件层，不放在页面层

**选择**：「无来源的建议不可被接受」这条规则由 `components/shared/` 里的确认条组件自身实现——它接受来源作为必需入参，来源缺失时组件内部即为禁用态并给出原因。

**理由**：这是产品可信度的核心规则。放在组件内部，页面就无法"忘记"检查；放在页面层，11 个页面里只要有一页漏写就破防。

**替代方案**：在简历建议页单独实现门禁判断。**否决**——规格 §2.1 明确要求该规则覆盖 P06/P08/P14 三处，单点实现无法保证。

### D4 · 沿用本地计算与 mock 数据，不引入数据层依赖

**选择**：在 `lib/` 下新增领域类型与 mock 数据模块，延续 `lib/jd-parse.ts` 已经在用的模式——纯函数 + 本地常量。

**理由**：现有 JD 解析就是本地规则实现且已可演示。保持同一模式，本变更不引入任何新依赖，也不制造与未来真实接口冲突的抽象层。

**替代方案**：引入 MSW 拦截请求，或先用 localStorage 持久化。**否决**——前者增加依赖与构建复杂度；后者会让"页面刷新后数据仍在"变成需要维护的行为，而本次目标是页面本身。

**替代方案**：直接接后端。**否决**——超出范围，且会阻塞前端进度。

### D5 · 路由按导航语义命名，而非规格编号

**选择**：

| 规格 | 路由 | 导航归属 |
|---|---|---|
| P07 资产档案总览 | `/resume` | 我的简历 |
| P08 简历导入与确认 | `/resume/import` | 我的简历 |
| P09 项目档案与证据提交 | `/projects/[id]` | 我的简历 |
| P10 深挖开始页 | `/projects/[id]/start` | 项目深挖 |
| P11 追问会话页 | `/projects/[id]/session` | 项目深挖 |
| P12 项目证据报告 | `/projects/[id]/report` | 项目深挖 |
| P13 差距与冲刺计划 | `/gap` | 职业差距分析 |
| P14 简历建议与专版简历 | `/resume/tailor` | 我的简历 |
| P15 账户设置 | `/settings` | 账户菜单 |
| P02 注册 | `/register` | 未登录 |
| P03 首次引导向导 | `/onboarding` | 首次登录 |

现有 `/resume`（占位）即 P07 的落点：把它从 `ModulePlaceholder` 改写成真实的资产档案页，简历导入与专版简历作为它的子路径。不另建 `/profile`。

**理由**：导航是用户定义的四个中文名（我的简历 / 意向职业 / 项目深挖 / 职业差距分析），路由应与之对应；规格编号（P07）是文档内部标识，不该出现在 URL 里。

**替代方案**：用 `/app/target/:id/gap` 这类规格原路径。**否决**——与现有扁平路由风格（`/dashboard`、`/target/new`）不一致，且 MVP 主目标唯一，路径里带 id 是多余复杂度。

### D6 · 追问会话的状态机在客户端组件内实现

**选择**：会话页用单个客户端组件持有状态（当前问题、轮次、回答、形成的证据、阶段：作答中 / 生成下一问 / 已结束），子组件按状态渲染。

**理由**：这是全站唯一有真实状态流转的页面（规格 P11 列了 5 种状态），且需要中断恢复。状态集中在单一组件内，比分散到多个组件再靠 props 串联更不容易出错。

**替代方案**：引入状态管理库。**否决**——单个页面的状态不值得引入依赖；且与现有"不引入状态管理库"的约定冲突。

## Risks / Trade-offs

**[信息密集页面在照片上的可读性]** → 追问会话与证据报告的文字量远大于工作台。**缓解**：沿用 `.ws` 的 `text-shadow`，并对长文本块使用 `--ws-ghost-box`（白 5% 底 + 极淡描边）而非卡片；若实施中仍不达标，缩小背景照片的可见区域而不是加遮罩。

**[无后端导致的状态不持久]** → 刷新后追问历史、任务状态会丢失，演示时会显得不完整。**缓解**：明确将其范围界定为"演示用本地数据"，在 tasks 中不安排持久化工作；若后续需要，作为独立变更处理。

**[组件抽取可能改动已完成的 4 个页面]** → 抽取共享组件时容易顺手改掉工作台现有实现。**缓解**：新组件放在 `components/shared/`，工作台在本次**不迁移**到新组件——先保证新页面可用，迁移留给后续变更。这是刻意的重复，换取不动已验证的页面。

**[`.ws` 是深色文字体系，与 shadcn 的浅色 `:root` 并存]** → 实现者可能误用 shadcn token（`bg-background`、`text-foreground`）导致某页突然变成浅色。**缓解**：新页面一律使用 `var(--ws-*)`；在 tasks 中把"不使用 shadcn 色彩 token"列为每页的检查项。

**[11 个页面的体量]** → 单个变更覆盖 11 页，实施周期长，中途容易失焦。**缓解**：tasks 按能力分组并排出依赖顺序，每完成一组即可独立验证；追问会话（P11）作为最高风险项优先安排。

## Migration Plan

纯增量，无数据迁移与破坏性变更：

1. 先落地 `components/shared/` 与 `lib/` 领域模型（被后续所有页面依赖）
2. 按能力分组实现页面：资产档案 → 项目深挖 → 差距分析 → 简历建议 → 账户与引导
3. 逐页替换 4 个占位页为真实内容
4. 每完成一组，跑一遍视觉一致性检查（对照现有 4 个页面）

**回滚**：新增文件不影响既有路由，回滚只需删除新增目录并把 4 个占位页恢复为 `ModulePlaceholder`。

## 与 `webdesigned.md` 的关系

> **这一节是补写的。** 本变更首次产出规划产物时，通篇没有引用 `.claude/rules/webdesigned.md`，
> 而 `CLAUDE.md` 明确要求「涉及架构、目录、数据库、核心依赖的修改，必须先参考这份规范」。
> 本变更动了目录、动了页面架构、动了全局样式，**完全落在"必须先参考"的范围内**。
> 补记于此，避免这笔账被当成"已经处理过了"。

完整符合度台账见 `docs/architecture/deviation-from-webdesigned.md`。就本变更而言：

### 本变更范围内、且已按规范执行的

| 规范条目 | 本变更的做法 |
|---|---|
| §12 目录规范 | `luod/` 迁至 `apps/web/`，建立 `packages/{types,config}`、`docs/`、`docker/`、`scripts/`，根工作区 `package.json` + `pnpm-workspace.yaml` |
| §13 模块化设计 | 共享件收在 `components/shared/`，页面按业务域分包，未跨模块乱调 |
| §19 禁止1（不换技术栈） | Next.js / React / TS / Tailwind / shadcn 结构原样保留 |
| §19 禁止2（不堆基础设施） | 未引入 Kafka / K8s / ES / 微服务；`apps/api`、`apps/worker`、`apps/ai` 只留 README 与触发条件，不建空脚手架 |

### 本变更范围内、**有意偏离**且必须记账的

| 条目 | 偏离内容 | 代价 |
|---|---|---|
| §3.1 / §4.2 | 未引入 TanStack Query、Zustand、Zod | 见下方「三项依赖」 |
| §11 | 无 `/api/v1`、无统一响应封套、无请求层 | 见下方「请求层」 |
| §14 | `lib/demo-auth.ts` 存明文演示密码 | 接真实认证时**第一优先级**清理 |
| §15 / §16 | 无测试、无可观测性 | 见下方「测试」 |

**三项依赖**：本次无任何 Server State（数据是本地常量），装 Query 属空转；
Client State 规模是单页面级 `useState`，装 Zustand 属过度设计；无不可信运行时输入，Zod 无对象可校。
这是有意的，但**不代表规范要求被满足了**。

**请求层**：11 个页面全部直接 `import` `lib/mock-data.ts` 与 `lib/session-seed.ts`。
接后端时这些 import 全部要换成请求调用，**届时应作为独立变更立项**，不要混在功能迭代里做。
判断与升级时机写在 `docs/architecture/frontend-conventions.md §1–§2`。

**测试**：`AGENTS.md` 要求"先补测试再改实现"，但本仓库无任何测试设施，
补测试需先引入框架，而 `CLAUDE.md` 禁止擅自引入第三方依赖——两条规则冲突。
本次未擅自引入框架，改用 `pnpm typecheck` + `pnpm build`（已关闭 `ignoreBuildErrors`）+
HTTP 渲染断言作为替代闸门。**这不等于测试。**
