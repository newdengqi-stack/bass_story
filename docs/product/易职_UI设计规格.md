# 易职 UI 设计规格（Offer 阶段）

> 本文档定义 **页面清单** 与 **每页展示的信息**。
> 上游依据：`docs/product/易职_Offer阶段_业务需求拆分.md`、`docs/product/易职_Offer_MVP_任务拆分与Agent设计.md`。
> 视觉层（配色、字体、动效）已另做 5 个候选方向（见 `site/variants.html`），**本规格只约束信息架构与交互，与选版解耦**——选定视觉方向后直接套用，不改结构。

---

## 0. 结论先行：需要做多少页面

| 分层 | 数量 | 说明 |
|---|---:|---|
| **MVP 核心页面（P0）** | **15** | 构成"目标岗位 → 项目验证 → 差距 → 简历"最小闭环，缺一不可 |
| **P1 增强页面** | **4** | 面试复盘、模拟训练、资源库、多岗位管理；增强循环与留存 |
| **系统层** | **3 项** | 404/错误页 + 空态与加载态规范 + 全局搜索（后两者是组件规范，不占独立页面） |
| **合计独立页面** | **19** | 另有 3 项全局组件规范 |

P2（语音面试、真人导师、私有仓库、岗位抓取、投递管理）不进入本规格。

## 2. 全局约定

### 2.1 信息架构层（本规格强制）

| 约定 | 说明 |
|---|---|
| **主目标唯一** | 任何时刻仅一个主目标岗位；所有报告、证据卡、简历版本均绑定它并显示岗位名 |
| **状态可见** | 四种证据状态（已验证 / 用户声明 / 证据不足 / 当前缺失）必须在任何出现能力的界面可见，且带来源 |
| **可追溯** | 每条结论旁必须能展开看到来源（追问轮次 / 材料 / GitHub / 用户填写） |
| **硬条件不混淆** | 学历、年限等硬性条件单独分区展示，不与可补强能力混排 |
| **禁止无来源的强化表述** | 界面上任何"建议写入简历"的内容必须可点开看来源，无来源则不可操作 |
| **空态有出口** | 每个列表/报告为空时，必须给出一个明确的下一步动作 |

### 2.2 全局组件清单

| 组件 | 用途 | 出现页面 |
|---|---|---|
| 顶部导航 | 品牌 + 主导航 + 主目标切换 + 账户 | 全部应用页 |
| 主目标条（Context Bar） | 常驻显示当前主目标岗位名，点击可切换 | 全部应用页 |
| 证据状态标签 | 四状态色块/标签 | P09 P11 P12 P13 P14 |
| 来源浮层 | 悬停/点击展开结论来源 | P11 P12 P13 P14 |
| 步骤指示器 | 引导向导、深挖会话进度 | P03 P11 |
| 任务卡 | 冲刺任务（目标/时长/完成定义） | P04 P13 |
| 空态块 | 列表为空时 | 全部列表页 |
| 确认/拒绝操作条 | 逐条接受、编辑、拒绝 | P06 P08 P14 |
| 全局搜索（⌘K） | 跳转页面、项目、岗位 | 全部应用页 |

### 2.3 全局状态规范

| 状态 | 规范 |
|---|---|
| **加载** | 已知结构的列表/卡片用骨架屏；AI 分析类（JD 解析、追问生成、报告生成）用带文案的进度提示，需说明"正在做什么"，超过 10 秒给出预计等待 |
| **空** | 一行说明"空的是什么" + 一行说明"为什么重要" + 一个按钮 |
| **错误** | 说清：发生了什么 / 为什么 / 怎么办。不得暴露技术细节。AI 失败时保留用户已输入内容，提供重试 |
| **权限** | P1 及以后如有角色区分，权限不足与系统错误必须分开提示 |
| **部分成功** | JD 解析、简历解析部分失败时，允许用户先确认已成功部分，失败项单独标注 |

### 2.4 响应式断点

| 断点 | 布局变化 |
|---|---|
| ≥ 60rem | 桌面：双栏（主内容 + 侧栏） |
| 40–60rem | 平板：侧栏折叠到主内容下方 |
| < 40rem | 手机：单栏；导航收为按钮；证据侧栏改为底部抽屉 |

追问会话页在手机上必须**保持单题聚焦**，证据侧栏默认收起。

## 3. 逐页规格

> 每页给出：路由 · 优先级 · 对应需求 Task · 页面目标 · 入口 · 区块结构 · **展示信息** · 操作 · 状态。

### P01 · 落地页

- **路由** `/` · **优先级** P0 · **需求** 无（业务补充）
- **目标**：向未注册用户讲清"证据化求职准备"是什么，驱动注册
- **入口**：外部访问

**区块结构**
1. 顶部导航（品牌 + 登录 + 注册）
2. 首屏：价值主张 + 副文案 + 主 CTA
3. 四阶段流程说明（对应闭环）
4. 四种证据状态说明
6. 底部 CTA

**展示信息**

| 内容 | 说明 |
|---|---|
| 价值主张 | 一句话，不含未兑现承诺 |
| 副文案 | 面向"嵌入式校招/实习"的定位说明 |
| 四阶段 | 建目标岗位 → 项目验证 → 差距计划 → 专版简历 |
| 四状态 | 已验证 / 用户声明 / 证据不足 / 当前缺失 及各自含义 |
| 承诺清单 | 结论可追溯、排序可解释、任务 < 90 分钟、简历建议逐条确认 |

**操作**：主「开始准备」（→ 注册）· 次「登录」

**状态**：无需登录即完整可读；不做虚构数据（无用户量、成功率等无来源数字）

---

### P02 · 登录 / 注册

- **路由** `/login`、`/register` · **优先级** P0 · **需求** 业务补充
- **目标**：完成身份认证，建立会话
- **入口**：落地页 CTA、受保护页重定向

**区块结构**：品牌区 · 表单区 · 切换登录/注册

**展示信息**

| 字段 | 类型 | 校验 |
|---|---|---|
| 邮箱 | 文本 | 必填、格式、长度上限 |
| 密码 | 密码 | 必填、最小长度；注册时显示强度提示 |
| 确认密码 | 密码 | 仅注册；一致性校验 |
| 同意条款 | 勾选 | 注册必选 |

**操作**：主「创建账户」/「登录」· 次「忘记密码」（后置）· 切换链接

**状态**
- 加载：提交中禁用按钮，防重复提交
- 错误：认证失败不区分"邮箱不存在 / 密码错误"（安全要求）
- 成功后：无主目标 → 进引导向导；有主目标 → 进工作台

---

### P03 · 首次引导向导

- **路由** `/onboarding` · **优先级** P0 · **需求** 流程 A（T3/T4/T10/T14/T27 串联）
- **目标**：让用户在 5 分钟内拿到"绑定 JD 的第一份差距报告"——完成定义是「有报告」，不是「上传了简历」
- **入口**：首次注册后、或工作台无主目标时的引导

**区块结构**（四步，可前进后退，步骤指示器常驻）
1. 步骤 1：建立主目标岗位
2. 步骤 2：导入简历
3. 步骤 3：确认解析出的项目与技能
4. 步骤 4：选择一个代表项目 → 提交材料 或 直接开始追问

**展示信息**

| 步骤 | 展示信息 |
|---|---|
| 1 | 岗位名称、JD 输入框、JD 必填校验提示、可保存的草稿状态 |
| 2 | 简历文本输入区、文件上传入口（标注"PDF/DOCX 后置"）、解析进度 |
| 3 | 解析出的项目列表、技能列表，均标注初始状态"用户声明" |
| 4 | 项目卡片（选择用）、GitHub 链接输入、材料提交入口、追问入口 |
| 全程 | 当前步骤 / 总步骤、离完成还差什么 |

**操作**：主「下一步」/「完成」· 次「上一步」· 逃生口「暂时跳过」

**状态**
- 跳过提示：明确告知"跳过后不会有差距报告，可稍后在档案页补齐"
- 解析失败：允许手工录入项目与技能，不阻断流程
- 完成：跳转差距报告页，并提示"这就是你绑定 JD 的第一份报告"

### P04 · 工作台（Dashboard）

- **路由** `/app` · **优先级** P0 · **需求** 状态机（需求书 §6）+ 全链路入口
- **目标**：一眼看清"我在哪一步、下一步做什么"
- **入口**：登录后、导航品牌位

**区块结构**
1. 当前主目标卡（含切换）
2. 准备状态机进度条
3. 下一步任务（1–3 条）
4. 证据概览
5. 差距摘要
6. 简历状态
7. 最近活动时间线

**展示信息**

| 区块 | 字段 |
|---|---|
| 主目标卡 | 岗位名称、公司/行业、工作地点、投递截止、优先级、JD 是否已确认 |
| 状态机 | 当前阶段 + 已完成阶段：未开始 → 已建立目标岗位 → 已导入候选人资产 → 已完成项目验证 → 已生成冲刺计划 → 简历就绪 → 模拟面试准备中 → 真实投递/面试中 |
| 下一步任务 | 任务标题、所属能力、预计时长、完成定义、来源（差距报告 / 复盘） |
| 证据概览 | 各项目名 + 四种证据状态计数 + 最近验证时间 |
| 差距摘要 | 可强调 / 待补证据 / 当前缺失 各计数；硬性条件单独一行 |
| 简历状态 | 是否已生成岗位专版、版本号、生成时间、绑定岗位 |
| 活动时间线 | 最近 N 条：追问完成、任务完成、报告生成、复盘录入，含时间 |

**操作**：主「继续下一步」· 次 各区块的跳转链接 · 切换主目标

**状态**
- 空（无主目标）：整页替换为引导卡 + 「创建主目标岗位」
- 空（有主目标无项目）：证据区给"添加一个项目"出口
- 局部失败：某区块数据取不到时该区块单独降级，不影响整页

### P05 · 目标岗位创建

- **路由** `/app/target/new`（编辑：`/app/target/:id/edit`） · **优先级** P0 · **需求** T1/T3/T4
- **目标**：录入一份具体 JD 作为准备基准
- **入口**：工作台、导航、引导向导步骤 1

**区块结构**：基本信息 → JD 原文 → 可选信息 → 提交

**展示信息**

| 字段 | 必填 | 说明 |
|---|---|---|
| 岗位名称 | ✅ | 用于报告与简历版本命名 |
| JD 原文 | ✅ | 多行文本；**未填写不得进入分析** |
| 公司 / 行业 | — | 可选 |
| 工作地点 | — | 可选 |
| 投递截止时间 | — | 可选，用于时间紧迫度排序 |
| 优先级 | — | 高 / 中 / 低 |
| 设为当前主目标 | — | 开关，默认开 |

**操作**：主「分析这份 JD」· 次「保存草稿」

**状态**
- 校验错误：JD 为空时按钮禁用并说明原因
- 分析中：按钮进入加载，显示"正在抽取岗位要求"
- 分析失败：保留 JD 原文，提供重试与"仅保存不分析"

---

### P06 · JD 解析确认

- **路由** `/app/target/:id/review` · **优先级** P0 · **需求** T5/T6/T7
- **目标**：让用户修正解析错误，避免基于错误判断准备方向
- **入口**：P05 分析完成后

**区块结构**
1. 左：JD 原文（可折叠）
2. 右：解析结果四分组
3. 底部：确认条

**展示信息**

| 分组 | 字段 |
|---|---|
| 技术标签 | 标签名、类别、**来源片段**、**抽取方式**（AI / 规则 / 用户补充）、**要求强度**（必须 / 加分 / 推断）、**置信度** |
| 项目经验要求 | 要求描述、来源片段、要求强度、置信度 |
| 工程能力 | 能力名、来源片段、要求强度、置信度 |
| 硬性条件 | 学历、专业、年限 —— **独立分区，标注"不可用项目弥补"**，走规则通道 |
| 待确认区 | 置信度低于阈值的标签默认折叠在此，等待用户逐条放行 |
| 全局提示 | 未在 JD 中出现的技术不得标为"明确要求"；**推断项必须标注"岗位名称推断"，默认不参与差距判定** |

每个标签支持：编辑、删除、新增（手工补充，抽取方式记为"用户补充"）。
详见 §7.1 JD 标签提取策略。

**操作**：主「确认并设为主目标」· 次「重新解析」「返回修改 JD」

**状态**
- 全部被删空：提示"至少保留一项要求，否则无法生成差距报告"
- 重新解析：需二次确认，说明会覆盖当前修改

### P07 · 资产档案总览

- **路由** `/app/profile` · **优先级** P0 · **需求** T9/T11/T12 → 汇总入口
- **目标**：集中管理可复用的候选人资产，避免为每份 JD 重复填写
- **入口**：导航、工作台

**区块结构**：简历卡 → 项目列表 → 技能清单 → 教育经历

**展示信息**

| 区块 | 字段 |
|---|---|
| 简历卡 | 来源（粘贴/文件）、导入时间、解析状态（待确认 / 已确认）、解析出项目数、技能数 |
| 项目卡（列表） | 项目名、个人角色、技术关键词、证据状态汇总（如"2 已验证 / 1 缺失"）、是否已提交 GitHub 或材料、最近验证时间、是否为当前验证项目 |
| 技能清单 | 技能名 + 来源标注（简历 / 项目 / 用户声明） |
| 教育经历 | 学校、专业、学历、起止时间 |

**操作**：主「导入简历」「新增项目」· 次 每个项目的「设为当前验证项目」「进入深挖」

**状态**
- 空：引导卡 + 「导入简历」
- 解析结果未确认：卡片标记"待确认"，并在上方给出统一确认入口

---

### P08 · 简历导入与确认

- **路由** `/app/profile/resume` · **优先级** P0 · **需求** T10/T11/T12
- **目标**：导入简历并逐条确认识别出的内容
- **入口**：档案总览、引导向导步骤 2

**区块结构**：导入区 → 解析结果区（分组可编辑）→ 确认条

**展示信息**

| 分组 | 字段 | 每条操作 |
|---|---|---|
| 技能 | 技能名、来源片段 | 确认 / 编辑 / 删除 |
| 项目条目 | 项目名、个人角色、时间区间、描述要点 | 确认 / 编辑 / 删除 |
| 教育经历 | 学校、专业、学历、时间 | 确认 / 编辑 / 删除 |
| 其他 | 奖项、证书 | 确认 / 编辑 / 删除 |
| 全局提示 | **"解析只是提取，不是验证；初始状态均为用户声明"** | — |

**操作**：主「确认全部」· 次 逐条操作 · 「重新导入」

**状态**
- 解析为空：提示手工录入，不阻断
- 部分失败：成功项可用，失败项单列并允许手工补
- 重复导入：提示将替换现有简历解析结果，需确认

### P09 · 项目档案与证据提交

- **路由** `/app/projects/:id` · **优先级** P0 · **需求** T13/T14/T15/T16
- **目标**：建立项目档案并提交支撑材料
- **入口**：档案总览、工作台

**区块结构**：项目基本信息 → 证据材料 → 已提交清单 → 进入深挖

**展示信息**

| 分组 | 字段 |
|---|---|
| 项目基本信息 | 项目名称*、项目目标、个人角色/贡献、时间区间、技术关键词、项目描述 |
| 链接类证据 | GitHub 公开仓库链接（可选，仅保存不做深度分析） |

## 7. 附录：两项已定策略

### 7.1 JD 标签提取策略（对应 Q1）

**结论：两者结合，以"可回链"为架构约束——规则定边界、AI 填语义、用户做终审。**

不是"AI 抽完再拿规则校验"的拼接。规则不是事后检查器，而是准入条件：一个候选标签必须先满足规则定义的准入，才允许成为标签。

**为什么不能纯 AI**

需求书 4.1 有一条硬规则：

> 未在 JD 中出现的技术，不得被标为「明确要求」。

纯 AI 抽取从原理上违反它——模型会基于「嵌入式岗位通常要 C 语言」这类先验，补出 JD 里根本没写的标签，且给出的理由听起来很合理。这条规则是产品可信度的地基，不能靠模型自觉。

**为什么不能纯规则**

JD 写法千变万化：「熟悉 CAN 总线者优先」/「有 CANoe 使用经验加分」/「掌握车载网络通信」——纯词表要么漏召回，要么把「加分项」和「必须项」混为一谈。且归入「技术 / 项目经验 / 工程能力 / 硬条件」四类本质是语义分类，规则做不好。

**职责分工**

| 职责 | 承担方 |
|---|---|
| 语义分句、归入四类 | AI |
| 同义词归一（FreeRTOS → RTOS、「实时操作系统」→ RTOS） | AI 判断 + 词典纠偏 |
| 判断语气强度（必须 / 加分 / 优先） | AI |
| **每个标签必须回链到 JD 原文片段（span）** | **规则（强制准入）** |
| 硬条件（学历、专业、年限） | **规则**（正则 + 学历/年限词表，独立通道） |
| 兜底召回常见嵌入式术语 | 规则（词表） |
| 类别必须是四类枚举之一 | 规则（allow-list） |
| 最终确认 | 用户（T6） |

**两条关键设计**

1. **硬条件独立走规则通道。** 学历、专业、年限直接决定「这个岗位我够不够格」的结论，出错代价最高，而其文本模式又最固定（`本科|硕士|博士|统招|985|211|\d+\s*年`）。单独通道，输出稳定可测。

2. **标签分两级，不是一级。**
   - *JD 明确要求*：可回链到原文 span，进入差距报告的正式比对
   - *岗位推断项*：如「嵌入式软件工程师」推断出 C 语言，必须显式标注来源为「岗位名称推断」，**默认不参与差距判定**，用户勾选后才生效

   这一条直接服务于硬规则——不是禁止推断，而是推断的东西不能伪装成 JD 写过的。

**失败与降级**

AI 不可用或超时 → 退化为纯规则模式，仍产出基础标签（技术词表 + 硬条件正则），**不阻断用户**；界面标注「本次为快速解析，可能有遗漏，可手工补充」。对应 P06 与状态矩阵的「部分成功」。

**标签数据结构（供实现参考）**

```text
标签 = {
  名称, 类别(技术|项目经验|工程能力|硬条件),
  来源片段(span), 抽取方式(AI|规则|用户补充),
  要求强度(必须|加分|推断), 置信度, 解析版本
}
```

保留解析版本是需求书 §7.3-5「所有 Agent 输出必须结构化保存，并保留输入来源、结论版本和证据状态」的要求。

**代价**：一次解析 = 一次模型调用 + 一次规则后处理。复杂度集中在规则层（词表维护、span 对齐），可控且可测试——比让模型自己保证不幻觉便宜得多。

### 7.2 冲刺任务时长策略（对应 Q4）

**结论：规则定档位、AI 定内容。**

**为什么时长必须固定档位**

- 时长是「我现在能不能立刻开始做」的决策依据，需要可比较、可排序、可信
- AI 生成「预计 43 分钟」是虚假精确，与产品「不虚构」的主张直接冲突
- 固定档位让用户建立直觉（「这是个 30 分钟的活」）
- 便于按剩余时间筛选（「我还有半小时」）

**档位与职责划分**

时长档位固定为 **15 / 30 / 45 / 60 / 90 分钟**，由规则按任务类型映射：

| 任务类型 | 档位 |
|---|---|
| 补充材料、截图、整理链接 | 15 |
| 读一段官方文档并整理要点 | 30 |
| 回答追问中的某个具体问题 | 45 |
| 补一个小实验 / 写一段代码验证 | 60 |
| 重做某个模块的实现说明 | 90 |

AI 负责**内容**：任务标题、任务目标、完成定义、再次验证方式、关联能力标签。

**硬约束**

需求书 4.4 要求任务小于 90 分钟，因此档位上限即 90 分钟。规则判定任务规模超过 90 分钟时，必须**拆分为多条任务**，不允许生成超档位任务。
