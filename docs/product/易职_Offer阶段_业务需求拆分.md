# 易职 Offer 阶段业务需求拆分

## 1. 当前产品边界

易职当前只服务于已经进入实习/校招准备期、希望提升目标岗位面试机会和 Offer 概率的嵌入式求职者。

暂不解决“我适不适合嵌入式”“该学 MCU 还是 Linux”“完整学习路线是什么”。这些能力保留为后续阶段。当前用户已经有学习经历、项目或基础技术栈，需要把它们变成可验证、可表达、可匹配岗位的求职能力。

**产品可控目标：** 让用户在目标岗位下拥有经得起追问的项目证据、明确的能力差距、可信的简历版本和可迭代的面试准备计划。

**产品不承诺：** Offer、面试邀请、内推、代投或绕过学历与市场竞争。

## 2. 核心业务闭环

```text
选择目标岗位并提交 JD
          ↓
导入简历和已有项目
          ↓
收集项目证据（GitHub / 材料 / 多轮追问）
          ↓
验证项目深度，映射目标岗位要求
          ↓
生成差距与冲刺计划
          ↓
形成基于证据的岗位简历
          ↓
模拟面试 / 真实面试复盘
          ↓
更新项目证据、差距优先级与下一步任务
```

这不是线性一次性流程。用户在真实面试中被问住后，应回到“项目证据验证”或“差距计划”，而非重新开始。

## 3. 参与角色

| 角色 | 主要目标 | 在系统中的动作 |
| --- | --- | --- |
| 求职者 | 获取更匹配的面试机会并提升通过率 | 提交 JD、简历与项目材料；完成追问和任务；记录面试反馈 |
| 易职 Agent | 提供可追溯的诊断与行动建议 | 解析 JD、发起追问、判断证据状态、生成计划与简历建议 |
| 内容/规则运营（后续） | 保持岗位标签和评价规则有效 | 审核高频 JD 标签、维护追问模板与外部资源 |
| 导师/专家（后续，可选） | 处理高价值人工评审 | 对用户主动申请的报告或模拟面试给出人工反馈 |

首版只有“求职者 + Agent”两个实际参与角色；不要在 MVP 中引入导师排班、企业账号或复杂运营后台。

## 4. 业务域拆分

### 4.1 求职目标管理

**解决什么：** 用户要准备的不是抽象“嵌入式”，而是一份具体 JD 或一个同类岗位集合。

**输入：** 岗位名称、公司/行业（可选）、JD 原文、投递截止时间、地点、优先级。

**处理：** 抽取技能、项目、工程能力、学历/年限等要求；映射为岗位能力标签；允许用户修正解析错误。

**输出：** 一个“当前主目标岗位”，以及对该岗位的能力清单。

**规则：**

- 用户可保存多个岗位，但同一时刻仅有一个主目标；所有报告和任务均绑定主目标。
- 未在 JD 中出现的技术，不得被标为“明确要求”。
- 学历、年限等硬条件必须单独展示，不假装能用项目弥补。

### 4.2 候选人资产档案

**解决什么：** 集中保存简历、项目和用户自己的能力声明，避免为每份 JD 重复填写。

**输入：** 简历文本/文件、项目基本信息、个人角色、技术关键词、GitHub 公开链接或项目材料。

**处理：** 提取项目和技能；要求用户确认；所有内容初始状态均为“用户声明”。

**输出：** 可复用的候选人资产库。

**规则：** 简历解析只是提取，不是验证；用户可删除或修改解析结果。

### 4.3 项目证据验证（核心业务）

**解决什么：** 判断用户是否能真正解释简历中的项目，而不是只把项目改写得更漂亮。

**证据来源：**

1. 公开 GitHub 仓库链接。
2. 用户主动提交的项目文档、设计图、日志、代码片段。
3. 在没有材料时完成的多轮项目追问。

**验证维度：** 项目目标、个人贡献、架构/数据流、技术选型、关键实现、调试定位、异常处理、工程质量、局限与改进。

**输出：** 项目证据卡；每个能力标签都带有来源、追问记录和状态。

**证据状态：**

| 状态 | 含义 | 可否写入简历 |
| --- | --- | --- |
| 已验证 | 有材料或连续追问支持，用户能解释清楚 | 可以 |
| 用户声明 | 用户在简历/表单中填写，但无验证支撑 | 不直接写成强化表述 |
| 证据不足 | 材料不完整或回答无法支撑结论 | 不可以 |
| 当前缺失 | 与目标岗位相关但用户目前没有 | 不可以，进入差距计划 |

### 4.4 岗位差距诊断与冲刺计划

**解决什么：** 用户知道自己离目标岗位缺什么，以及有限时间内先补什么。

**输入：** 主目标 JD 的能力标签、候选人资产、项目证据状态、求职剩余时间、真实面试反馈。

**处理：** 计算每项能力的岗位相关性、证据状态、准备成本与时间紧迫度；生成排序。

**输出：**

- 已具备且可强调的能力。
- 与岗位有关但需补证据的能力。
- 当前缺失且必须处理的能力。
- 小于 90 分钟的下一步任务，包含完成定义和再次验证方式。

**规则：** 计划不等于完整课程。优先给项目补强、定向练习、官方文档/外部资源和复盘任务；不承诺短期内掌握复杂技术。

### 4.5 可信简历生成与管理

**解决什么：** 让用户简历更匹配岗位，同时降低过度包装导致的面试风险。

**输入：** 原始简历、主目标 JD、项目证据卡、用户确认过的事实。

**处理：** 对项目要点、技术关键词和个人贡献提出逐条修改建议；展示每条建议的证据来源与原文差异。

**输出：** 岗位专版简历草稿，以及用户可接受/编辑/拒绝的修改记录。

**规则：**

- 未验证的技术、指标、成果和职责不可自动写入。
- 用户最终确认后才生成/导出版本。
- 生成版本必须绑定主目标岗位，防止一份简历泛投所有岗位。

### 4.6 面试训练与复盘

**解决什么：** 把项目问题、基础知识、算法和真实面试反馈，持续回灌到用户的冲刺计划。

**输入：** 主目标 JD、项目证据、差距报告、用户主动记录的真实面试问题。

**处理：**

- 项目追问：基于用户真实项目深挖，而非随机出题。
- 基础题/算法：按 JD 能力标签与当前缺口生成练习。
- 真实面试复盘：将问题、答题情况与卡点映射为能力标签和新任务。

**输出：** 面试准备清单、模拟追问结果、复盘记录、更新后的差距优先级。

**规则：** 首版优先文字追问与复盘；语音模拟、真人面试和复杂算法判题是后续能力。

### 4.7 外部资源与知识服务

**解决什么：** 为差距计划提供可信的下一步学习入口，而不是建设第二个大型课程平台。

**输入：** 能力缺口、目标岗位、用户当前阶段。

**输出：** 精选官方文档、开源项目、文章、练习题或任务说明。

**规则：** 资源必须注明来源与适用前提；不复制第三方付费课程内容；外部资源不能替代用户的项目验证。

## 5. 关键业务流程

### 流程 A：首次进入 Offer 冲刺

1. 用户点击“准备实习/校招”。
2. 创建或选择主目标岗位，粘贴 JD。
3. 导入简历，确认解析出的项目与技能。
4. 选择一个最能代表自己的项目，提交仓库/材料或开始追问。
5. 系统生成首份岗位差距报告和一个下一步任务。

**完成定义：** 用户拥有一个绑定 JD 的报告，而不只是上传了一份简历。

### 流程 B：项目深挖

1. Agent 读取目标岗位要求和项目档案。
2. 按“目标 → 架构 → 选型 → 实现 → 调试 → 改进”进行单题追问。
3. 用户可回答、跳过或声明未做过。
4. Agent 标记证据状态，说明结论依据。
5. 用户获得项目证据卡和需补强的问题清单。

**完成定义：** 至少形成 5 条有来源的证据/缺口，而非泛泛评分。

### 流程 C：简历修订

1. 用户从差距报告进入“生成目标岗位简历”。
2. 系统只使用已验证事实提出修改建议。
3. 用户逐条确认、编辑或拒绝。
4. 保存为该岗位专版简历。

**完成定义：** 每条新增或强化表述都能追溯到原材料或评估记录。

### 流程 D：真实面试后的回流

1. 用户记录被问问题、自己的回答和卡点。
2. 系统映射到项目、基础知识、算法或表达能力标签。
3. 差距报告生成新版本，任务优先级调整。
4. 用户完成任务后再次验证，保留前后变化。

**完成定义：** 面试失败转化为可执行的下一次准备动作。

## 6. 核心状态机

### 用户 Offer 准备状态

```text
未开始
  → 已建立目标岗位
  → 已导入候选人资产
  → 已完成项目验证
  → 已生成冲刺计划
  → 简历就绪
  → 模拟面试准备中
  → 真实投递/面试中
  → 复盘后回到项目验证或冲刺计划
```

### 业务完成标准

用户并非在“拿到 Offer”时才算完成；一个有效准备闭环完成于：目标岗位明确、至少一个项目完成验证、差距计划生成、岗位专版简历经用户确认、并完成至少一次复盘或模拟追问。

## 7. MVP 优先级

| 优先级 | 业务能力 | 说明 |
| --- | --- | --- |
| P0 | 主目标 JD、简历/项目资产、文字项目追问、证据状态、差距报告、下一步任务 | 必须形成可信准备闭环 |
| P0 | 基于证据的简历修改建议 | 与核心闭环直接相关，先提供文本版本 |
| P1 | 模拟面试、真实面试复盘、外部资源映射 | 增强循环与留存 |
| P1 | GitHub 结构分析、PDF/DOCX 导出、提醒 | 提高效率，不决定核心价值 |
| P2 | 语音面试、真人导师、私有仓库、岗位抓取、投递管理 | 成本/合规/复杂度高，后置 |

## 8. 业务指标

| 层级 | 指标 | 初始目标 |
| --- | --- | ---: |
| 激活 | 创建主目标岗位、导入简历并启动一个项目评估 | 60% |
| 核心完成 | 获得首份差距报告 | 45% |
| 可信产出 | 保存一份证据化岗位简历 | 35% |
| 循环 | 7 日内完成任务或录入复盘 | 30% |
| 质量 | 用户认可“结论有依据，不虚构能力” | 4/5 |

面试邀请率与 Offer 率只能作为长期结果指标，必须结合学历、地点、行业、岗位数量、投递量和招聘周期分析，不能直接归功于产品。

## 9. 当前不再讨论的需求

以下需求记录为后续方向，不进入本轮 Offer MVP：

- 从兴趣出发的职业探索。
- 完整的 MCU、Linux 应用、Linux 驱动学习路线。
- 大规模自建课程、题库与社区。
- 泛化学习答疑 Agent。

它们未来可复用“用户画像、项目证据、能力标签、任务与复盘”的基础数据，但不能抢占当前 Offer 业务的开发资源。
