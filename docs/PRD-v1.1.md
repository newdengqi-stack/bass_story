## 1. 产品摘要、目标与边界

### 1.1 一句话定义

面向计算机类大学生，通过**简历理解、岗位分析、基础与项目混合诊断、可解释能力画像**，发现真实或待验证的能力差距，并给出**现在做 / 以后做 / 当前不建议重点投入**的求职成长建议和真实的简历增强建议。

### 1.2 用户要完成的工作（JTBD）

> 当我准备找技术岗实习或校招工作、却不清楚自己水平和项目竞争力时，我希望通过已有简历和一轮有针对性的技术交流，知道哪些优势能支撑目标岗位、哪些部分需要进一步验证或补强，以及在有限时间内怎样安排下一步行动。

### 1.3 核心价值闭环

`简历及经历 → 用户确认的技能/项目声明 → 选择或探索岗位 → 技术能力诊断 → 有证据的能力画像 → 对照岗位要求 → Gap → 行动优先级 → 真实简历增强 → 复测/持续更新`

### 1.4 目标

- **认知**：用户能够区分已验证优势、已验证薄弱点、尚未验证项目；查看依据而非只看分数。
- **岗位**：用户能够理解与某个明确岗位或通用岗位模板之间的具体差距。
- **取舍**：每次报告优先指出 1–3 件最值得采取的行动，以及有理由的暂缓项。
- **表达**：挖掘真实项目中的个人贡献与技术细节，提供不虚构事实的简历文本增强建议。
- **成长**：支持用户保存计划，完成实践后通过新增证据/专项复测更新能力状态。

### 1.5 非目标与不可承诺事项

- V1 **不预测个人获得面试、录用或 Offer 的概率**，不保证求职结果。
- V1 **不把模型分数表述成官方技能认证**，不提供具有法定效力的证书。
- V1 不分析或执行用户源代码、不抓取 GitHub 仓库、不自动投递职位。
- V1 不做泛专业职业测评、面向全行业/全岗位的能力画像，不做完整在线课程平台。
- V1 不一键生成虚构经历、虚构结果、团队成果冒领或无依据的百分比提升。
- V1 不用学校名气、性别、年龄等与技能无关属性给技术水平打分；校招身份/学历等外部招聘门槛与技能评估分开呈现。

### 1.6 产品成功的最低判断

用户完成第一次诊断后，能明确回答：**我已有的优势是什么、证据不足的是什么、最影响当前目标岗位的缺口是什么、下一步具体做什么、暂时不值得优先投入什么**。这只是验收方向；实际效用需通过用户研究验证。

| ID | 假设 | 当前做法 | 验证方法 |

### 2.3 术语和统一约定

| 术语 | 定义 |
|---|---|
| `SkillClaim` | 用户或简历声明会某项技术；不是已验证的实际能力 |
| `SkillRubric` | 描述某技能达到 L1/L2/L3 所需的可观察行为与证据标准 |
| `assessed_level` | `null / L1 / L2 / L3`；`null` 表示当前不能充分授级 |
| `candidate_level` | 有初步支持、待交叉验证的候选等级 |
| `assessment_status` | `not_started / in_progress / partial / sufficient / insufficient_evidence / needs_review` |
| `performance_state` | `not_tested / insufficient_evidence / demonstrated_below_L1 / graded / disputed`；反映证据表现，不代替流程状态 |
| `review_status` | `draft_ai / pending_human_review / needs_revision / approved / rejected / published`；发布前审批状态 |
| `evidence` | 与实际题目、回答、用户确认事实或项目声明关联的可追踪观察 |
| `RoleProfile` | 技能 ID + 岗位重要度 `must/important/bonus/not_required` + 目标等级 |
| `Gap` | 用户当前已验证能力或证据状态与岗位要求/求职表达要求的差距 |
| `DEFER` | 当前阶段不建议**优先**投入；不是永久技术黑名单 |
| `P0/P1/P2` | 本文指产品开发优先级；计划任务的优先级也可使用相同标签，但属于不同对象 |

**统一裁决**：`assessed_level=null` 可表示未测、证据不足或经交叉验证低于 L1，必须联同 `performance_state` 解读。旧规范中 `assessed` 等状态值，仅在兼容层转换为 `sufficient`；正式新数据不写入 L0，也不把 null 当弱项。`L0` 可以出现在历史文案中，但不得作为新版本评估数值。

## 3. 目标用户、问题与使用场景

### 3.1 核心画像

- **用户 A：已有目标岗位**。大三/大四，简历列出 C、STM32、Linux 等技能，有明确岗位/JD，却不知道自己是否达到要求。
- **用户 B：方向尚不明确**。有若干项目，但不清楚更适合 C/C++、嵌入式还是 Linux 系统开发，需要可解释的方向建议。
- **用户 C：项目有内容但不会表达**。有实际技术贡献，但简历用“负责智能小车开发”等笼统句子，没有体现职责、选择、难点和结果。

### 3.2 用户关键问题与产品对应

| 用户问题 | 应提供的能力 | 验收观察点 |
|---|---|---|
| 我到底会什么、会到什么程度？ | 能力诊断 + 可解释证据 | 能展示哪些子技能已验证、哪些待验证 |
| 我适合哪些岗位？ | 岗位族推荐 + 推荐理由 | 有多个候选方向，不代用户做决定 |
| 我距目标岗位还差什么？ | JD/岗位模板 + Gap | 区分已验证缺口与证据不足 |
| 项目有没有含金量？ | 项目多维审查 | 区分技术深度、个人贡献、工程完整度、岗位相关性、可表达性 |
| 简历哪里不好？ | 内容、排版、项目表达分析 | 指出具体段落/结构问题及可执行修订 |
| 我应该先学什么，不学什么？ | Career Coach + DEFER | 给依据、替代方案、完成与复测标准 |

### 3.3 使用时点

- 即将开始找暑期/日常实习，准备评估自己的岗位准备度。
- 收到某公司的目标 JD，想做针对性检查。
- 已有项目但简历空泛，想挖掘实际贡献。
- 距离投递日期不远，需要短期取舍。
- 学习或完成项目后，希望知道是否真正补上缺口。

### 3.4 用户输入约束

大部分用户只有简历，项目材料可能不全。因此 V1 默认以**简历 + 补充问答**工作，不以 GitHub、代码 ZIP、成绩单等外部证明为必需条件。没有项目时仍可做知识与应用评估，但项目交付情况应保持“待验证”。

## 4. 用户旅程与核心业务流程

### 4.1 首次使用主流程（D-R2、D-R8 修订）

```text
V0 受控入口 → 用途告知/必要许可 → 求职状态选择
    ↓
文本 PDF 上传或粘贴简历 → 解析 → 用户确认技能、项目及个人贡献
    ↓
立即显示受限简历初评：六维非数值反馈/1～3 个具体问题
    ↓
确认岗位原型或粘贴 JD（允许只做通用基础诊断）
    ↓
开始 6～10 题的快速混合诊断（试验参数，不能承诺全面评估）
    ↓
提交成功：即时显示“待人工审核”及恢复查看方式
    ↓
AI 草稿 → 自动有效性检查 → 专家人工审批（D-R5）
    ↓
仅批准版本开放正式局部能力报告、已测/待测、局部 Gap、1～3 条行动建议
    ↓
可复制的真实简历改写建议 → 删除/到期清理
```

V1 再加入正式账号、历史档案、深度诊断、任务追踪和专项复测。未审核报告不得通过直接 URL、API 或缓存绕过发布闸门。

### 4.2 分支规则

- **有目标 + 有 JD**：基于具体 JD 生成需用户确认的岗位画像，优先评估 must 技能。
- **有目标 + 无 JD**：使用对应通用岗位模板，明确标注“通用岗位基线”。
- **目标不明确**：推荐首批岗位族中的 2–3 个方向，展示来自技能与项目的依据；用户选择其一才生成岗位导向 Gap/DEFER。
- **只是了解水平**：允许启动通用基础诊断，先输出能力概览；用户选择目标前不生成带强岗位结论的“暂不建议学什么”。
- **简历缺失或解析失败**：允许用户填写最小技能声明与项目描述，再进入受限诊断；记录资料完整性限制。
- **中途离开**：保存会话、问答与题目预算，允许恢复。
- **修改岗位**：创建新 Role/Gap/Plan 快照，不静默覆盖以前的能力证据。

### 4.3 核心时序约束

简历解析后的字段需经用户确认方可进入事实输入；项目是否本人完成由用户表述和追问形成证据，不能因为确认提取文本就宣称已经客观验证。诊断报告显示回答依据，并支持用户修订事实或复测技术判断。

## 5. 页面信息架构与交互约定

### 5.1 站点结构

```text
公共首页
├─ 产品介绍 / 说明 / 隐私提示
└─ 开始诊断
   ├─ 求职状态选择
   ├─ 简历上传或手动补录
   ├─ AI 理解确认（个人信息/技能/项目/简历问题）
   ├─ 目标岗位 / JD / 岗位推荐
   ├─ 诊断须知
   ├─ AI 技术问诊（暂停、跳过、澄清、恢复）
   └─ 结果报告
      ├─ 当前岗位准备概览
      ├─ 技术能力及证据
      ├─ 项目深度与贡献情况
      ├─ 简历质量与改写建议
      ├─ 岗位差距
      └─ 提升优先级与计划
个人求职档案（登录后）
├─ 目标岗位及已确认 JD
├─ 我的简历（版本与诊断记录）
├─ 我的能力（已评估/待验证）
├─ 我的项目（事实/贡献/表达）
├─ 我的计划（任务与专项复测）
└─ 设置（个人信息、隐私、导出/删除）
```

### 5.2 页面需求表

| 页面 ID | 页面 | 用户关键操作 | 系统关键反馈 | 必须处理的异常 |
|---|---|---|---|---|

| UI-02 | 求职状态 | 三种状态中选择 | 自动调整下步路径 | 用户不确定 |
| UI-03 | 上传简历 | 选文件、重传、手动补录 | 进度、成功、解析失败 | 不支持格式、超限、空白文档 |
| UI-04 | 信息确认 | 改技能、项目、贡献 | 显示来源片段及未确认项 | 提取错误、项目重复 |
| UI-05 | 目标岗位 | 选岗位、贴/传 JD、看推荐原因 | 标注 JD/模板来源 | JD 不完整、冲突、不在首批范围 |

| UI-07 | 诊断页 | 答题、澄清、跳过、暂停 | 题型主题、已记录、进度估计 | 模型超时、题目歧义、重复提交 |
| UI-08 | 诊断报告 | 看优势、薄弱点、依据 | 保守、可追踪的判断 | 证据不足时隐藏确定性结论 |
| UI-09 | Gap/计划 | 查看优先级、接受任务、查看暂缓理由 | 具体步骤、交付物、复测入口 | 时间约束变化、岗位切换 |
| UI-10 | 简历与项目建议 | 查看问题、事实补问、复制改写文本 | 原文/建议对比，明确未确认占位 | 无法确认的数字或贡献 |
| UI-11 | 我的档案 | 历史查看、专项复测、隐私操作 | 快照/版本变更说明 | 数据删除、失效资料 |

### 5.3 体验要求

- 诊断前说明：这是 AI 辅助评估，不是官方考试或录用保证。
- 用户可见的优先结论为“较强/一般/较弱/待验证”与文字解释，不展示难以理解的内部 confidence 值。
- 不在每题之后立即给标准答案，以免影响后续验证；可在结束后展示非泄题式反馈。
- 结果先给**结论与最重要的行动**，详细证据与所有技能折叠展开。
- 对缺信息只说“待验证”；跳过、不愿回答不等于技术错误。
- 支持桌面优先、移动端可阅读与答题的响应式体验；题目中的代码有等宽显示和换行策略。

### 6.3 P0 功能详细需求与验收

#### FR-01 用户身份与档案

- **输入**：注册/登录所需的最小身份信息；用户选择的年级、专业、求职状态（允许部分留空）。
- **处理**：创建独立数据空间，关联简历、诊断会话、岗位、历史计划；登录后可继续。
- **输出**：个人档案页；新用户空状态提示开始诊断。
- **验收**：不同账户不互相读取简历、答案和报告；用户退出后可恢复自身会话。

#### FR-02 求职状态与目标

- **输入**：明确岗位、不明确岗位、先了解技术能力三选一。
- **输出**：进入对应岗位确认/推荐/通用基础诊断分支。
- **验收**：未选择岗位时不得输出针对特定岗位的绝对判断或 DEFER 技术黑名单。

#### FR-03 简历上传与解析

- **输入**：PDF/DOCX（含文件名、格式、大小、页数等校验）。
- **处理**：提取基础信息、教育、实习、项目、技术、个人介绍、排版可检测信号与来源位置；保存原始文件和结构化快照的版本关联。
- **输出**：解析预览、字段来源、错误及不确定项提示。
- **验收**：解析失败不产生虚构数据；用户可重传/手动补录；不将无法解析的内容计为缺陷。
- **待定**：格式大小阈值、扫描 PDF 的处理策略在技术设计中确定；无法准确识别时主动降级。

#### FR-04 用户理解确认

- **输入**：AI 提取的技能、项目、经历、贡献说明。
- **处理**：用户逐项修订和确认；保存“提取原文”和“用户确认值”，并区分自述与 AI 已验证事实。
- **输出**：可进入诊断的 `CandidateSnapshot`。
- **验收**：用户否认某项目或某技能是自己做的，后续不再用该说法当作其独立贡献证据。

#### FR-05 简历基础诊断

- **内容维度**：必要信息完整性、技术经历清晰度、项目职责与动作具体性、个人介绍相关性、重复或空泛表述、可量化事实是否有来源。
- **排版维度**：已解析到的段落结构、标题层级、可检测的长度/字体/一致性与可读性问题；不得对无法可靠解析的排版给出确定负面评价。
- **输出**：简历基础质量概览、问题定位、分维度建议，必要时允许试验性分数，但不能混同为真实技术水平。
- **验收**：指出具体原文/位置与改进理由；解析不确定项标“无法准确判断”。

#### FR-06/07 目标岗位与 JD 解析

- **输入**：通用岗位模板，或用户粘贴/上传的目标 JD。
- **处理**：抽取技能、要求强度、职责、岗位性质；映射统一 Skill ID，保留原文片段、用户确认和解析版本。
- **输出**：`RoleProfile`，区分 `must / important / bonus / not_required`。
- **验收**：具体 JD 与通用模板冲突时，不盲目相加出不现实的全能岗位；冲突需要确认；无 JD 清楚标明基于模板。

#### FR-08 岗位方向推荐

- **输入**：用户确认的项目、技术声明、兴趣和现有证据。
- **处理**：在三个岗位族内生成候选方向，解释匹配线索与尚需验证内容。
- **输出**：可选择的 2–3 个方向和推荐理由；不输出冒充录用率的百分比。
- **验收**：必须允许用户拒绝或更换推荐；“用户没写 Linux”不能被当作已验证的弱点。

#### FR-09/10 AI 诊断与能力画像

- **输入**：用户确认的资料、岗位画像、Rubric、题目策略版本。
- **处理**：混合题规划、题目校验、文本答题、动态追问、证据入库、等级更新、停止与恢复。
- **输出**：已验证优势、关键错误、待验证项与每条结论的证据引用。
- **验收**：未答不扣分；单题 L1 正确不能直接升 L3；题目有歧义必须作废；相同答案重试不重复计分。

#### FR-11 项目多维诊断

- **输入**：项目介绍、个人职责声明、关键技术、用户对设计与问题的回答。
- **处理**：区分项目本身复杂度、用户个人贡献、技术自主性、工程完整性、岗位相关性及面试可解释性。
- **输出**：分维度优劣势、待确认事实与补问建议；证据不足时不强行给“含金量 85 分”。
- **验收**：识别“团队项目 ≠ 独立完成”；项目名字相同也可因贡献与技术证据不同产生不同结论。

#### FR-12 Gap 分析

- **输入**：技能快照、岗位快照、项目/简历快照及用户时间约束。
- **输出**：`skill_deficit / depth_deficit / practice_deficit / evidence_gap / project_gap / expression_gap / role_mismatch` 或 `met_requirement`。
- **验收**：`assessed_level=null` 时优先输出待验证，不计算等级差；换岗位只重算 Gap，不改原技能事实。

#### FR-13/14 Career Coach 与提升计划

- **输入**：Gap、岗位重要度、求职时点、可用时间与条件（允许留空）。
- **输出**：不超过 3 个首屏重点 P0 行动，次优先任务，1–3 个有根据的 DEFER（没有合理暂缓项可以不输出）。
- **每项行动**：原因、目标、2–5 步、交付物、验收标准、关联技能与复测方式；可接受/进行中/标记已做。
- **验收**：不能只说“多学 Linux”；用户勾选完成不会自动提升等级；若 JD 把某技术列为 must，不能无根据将其放入 DEFER。

#### FR-15 事实约束的文字增强

- **输入**：简历原句、用户补充事实、项目追问结果。
- **输出**：原句的问题、需确认事实、基于已知事实的建议改写文本（可复制），缺失内容使用显式待补占位。
- **验收**：不得无中生有添加“独立负责”“效率提升 40%”或不存在的项目；原始简历文件默认不被自动改写。

#### FR-16/17 历史复测与数据管理

- **输入**：专项技能复测请求、历史报告查看、个人数据删除请求。
- **处理**：为复测创建新会话与快照，保留历史版本；个人数据删除遵守实际发布的保留策略和适用法规。
- **验收**：复测不会覆盖历史证据；删除请求可执行、可审计，用户看到清楚的结果和处理范围。

## 7. 简历诊断、项目含金量与文本增强规则

> **目的**：把用户一开始明确提出的“排版、个人介绍、项目含金量、专业表达”需求完整纳入 PRD，避免产品过度偏向技术问答。

### 7.1 简历质量与用户能力分开

1. `ResumeQuality`：文档是否清晰、完整、可读、事实具体、能表达个人贡献。
2. `CandidateAbility`：通过 Rubric 和问答能证明的技术水平。
3. `JobReadiness`：与目标 RoleProfile 对照的准备程度。

三类数据**不互相代替**：优秀排版不能提升 C 指针等级，技术能力很强也不意味着简历表达已经合格。

### 7.2 简历质量维度（V1 初始配置）

| 维度 | 检查内容 | 数据限制 |
|---|---|---|
| 完整性 | 教育/联系方式/经历/项目等必要信息是否可识别 | 根据实习/校招类型判断，不要求无关字段 |
| 排版与可读性 | 标题层级、段落密度、文字一致性、可识别的格式问题 | 受 PDF/DOCX 解析精度限制 |
| 自我介绍 | 是否具体、是否围绕目标岗位、是否空泛 | 无自我介绍不必一律判低分 |
| 项目表达 | 是否说明任务、个人动作、技术、难点、结果 | 结果需有真实来源，不强制人人有量化数字 |
| 证据表达 | 技能是否有项目/实习/课程实践支撑 | “简历没有写”与“本人不会”分开 |
| 岗位针对性 | 经用户选择目标后才分析岗位相关性 | 必须说明 JD 或模板来源 |

**D-R3 强制变更**：V0 只展示六维分项文字评价（`clear/needs_improvement/unknown/not_applicable`）及具体证据，不展示任何 0–100 综合分；项目按 P-01 自身性质 / P-02 本人贡献 / P-03 岗位价值表达三层呈现。V1 若希望上线数值分，必须再次产品审批和专家校准。

**分数设计（历史目标，受 D-R3 约束）**：用户最初希望获得评分。V1 保留“简历基础质量分/分项评价”的产品能力，但**评分公式及权重在用户测试前视为试验性配置**。可以先提供“良好 / 需优化 / 无法判断”的分项反馈；若上线数值型 0–100 分，需展示评分口径、适用检测项、覆盖程度及版本，不把该分数包装成求职成功率或项目真实含金量。`JobReadiness` 单独展示，不混进简历基础分。

### 7.3 项目竞争力六维模型

| 维度 | 典型验证问题 | 特别注意 |
|---|---|---|
| 技术深度 | 使用哪些关键机制？为什么这样设计？ | 不等于堆砌技术关键词 |
| 技术/工程复杂度 | 需要处理哪些真实问题与约束？ | 不因项目名称普通就自动低评价 |
| 个人贡献 | 本人负责哪些模块，做了哪些决策？ | 团队整体成果不自动算个人成果 |
| 自主性 | 是跟教程、复用组件还是独立方案？ | 正常使用开源技术不构成负面项 |
| 工程完整度 | 调试、异常、测试、资源、安全、维护如何处理？ | 不要求实习生具备生产级全套流程 |
| 岗位相关与可解释性 | 能否说明项目如何支撑目标岗位？ | 相关性随岗位变化，理解能力随证据变化 |

**输出格式**：每维 `优势/待补充/有证据的缺口` + 1–2 条依据 + 可执行建议。不要用单个“项目含金量 87 分”取代全部判断。

### 7.4 项目增强与改写约束

```text
简历原句 → 抽取事实/贡献/技术/结果 → 用户确认或追问
     → 标记已知事实与待补事实 → 给出文字修改建议
     → 用户接受/复制 → 后续可进入完整编辑器（P1）
```

- 建议表达使用“问题/任务 → 本人动作 → 技术细节 → 结果/验证”。
- 没有测量数据不能添加虚构提升百分比。
- 无法确认本人责任的内容不能写成“独立主导/独立设计”。
- 不要求用户一定去做新项目；优先挖掘和补全已有项目的真实证据。

## 8. 能力诊断与 Assessment Agent 产品规则

### 8.1 六类输入

`CandidateSnapshot / ResumeSnapshot / SkillClaims / ProjectSummaries / RoleProfile / SkillRubrics + AssessmentPolicy`；后端负责绑定版本。

### 8.2 逻辑模块分工

| 组件 | 职责 | 明确禁止 |
|---|---|---|
| Orchestrator | 状态机、预算、重试、数据持久化和版本 | 任意改写评估事实 |
| Question Planner | 按岗位重要性、覆盖与不确定项规划题目 | 无限制追问和遗漏基础题 |
| Question Generator | 标准题+动态题；关联简历事实 | 生成不存在的用户项目事实 |
| Question Validator | 检查技术正确性、歧义、重题和问题范围 | 有歧义题继续计分 |
| Answer Evaluator | 按 Rubric 给结构化观测和关键错误 | 直接修改最终技能等级 |
| Skill State Evaluator | 融合证据、检查等级门槛、更新状态 | 把 null 判成弱项 |
| Report Builder | 输出可解释能力与待验证信息 | 宣称获面概率或编造证据 |

### 8.3 出题策略（初始假设）

- 完整的多技能首诊暂设 12–20 题的弹性预算。
- 初始题型比例：基础题 25%、声明验证 25%、项目题 30%、工程场景 20%，由岗位和证据动态调整。
- 基础覆盖是最低约束：不得只问简历写过的技术。
- 问题规划优先高重要度、尚未验证或有潜在关键误区的技能。
- 用户不答某题，可以跳过；用户表达模糊先尝试澄清。
- 题目生成必须关联 Skill/Subskill、目标等级、Rubric 版本、答案要点及用户资料来源。

### 8.4 评分与授级规则

- 单题可观察维度：技术正确性、理解深度、完整性、应用能力、推理与排查；不适用维度用 `null`。
- 初始权重 35/20/15/15/15 只是可配置测试策略；关键错误标志独立于数值。
- L1 要基础概念证据；L2 要独立应用或问题处理证据；L3 要深度分析和交叉验证。
- 无项目不能自动判定无法达到 L2，但“真实交付能力”仍需单独标示是否验证。
- 一份答案可以影响多个 Subskill，但不能因为共享证据就当成多个独立来源反复加权。
- `assessed_level=null`、`assessment_status=insufficient_evidence` 应呈现“待验证”。对于实际回答暴露的基础薄弱，可报告具体问题，不要伪称从未评估。

### 8.5 状态机

`created → awaiting_profile_confirmation → ready → planning → asking → awaiting_answer → evaluating → updating → (planning | paused | completed)`。

异常状态：`question_invalid / evaluation_retryable_error / needs_review / cancelled`。提交必须幂等；网络/模型重试不重复计分。被判技术无效的题目必须作废并可重抽。

### 8.6 例子：CL-04 指针

已讨论的指针演示中，用户基础解引用和指针传参正确，但误认为返回局部自动对象的地址后可以安全解引用。产品必须定位**对象生命周期存在关键误解**，保留基础正向证据，必要时暂评 L1 并把 L2 放在待验证状态，不能简单平均题分直接授 L2。

### 8.7 Rubric 范围与初版发布策略

- 统一技能域：C 14 节点 + C++ 10 + Linux 10 + MCU/嵌入式 10 + RTOS 7 + 工程能力 10，共 **61 个候选节点**。
- 节点注册与基本定义覆盖全域，但**P0 只要求每个领域选取 2–3 个与目标岗位高度相关的节点，补齐经过人工审校的正式 Rubric、题目蓝图和样例**；其余节点按覆盖状态展示待验证/尚未支持深入评估，不能伪装已全面检测。
- 详细 ID、Rubric、题型和技术边界以相关附属规范为准；上线前锁定相互兼容的版本组合。

## 9. 岗位画像、JD 解析与差距分析

### 9.1 岗位要求来源优先级

1. 用户确认的**具体 JD**（带原文依据）。
2. 经内部审阅的岗位族标准模板（无 JD 时使用）。
3. AI 基于经验提出但未核验的要求：只能标待确认，不可自动升为强制 must。

岗位要求与用户能力是不同数据：`RoleProfile` 变更不会修改 `UserSkillState`。

### 9.2 岗位族与边界

| 岗位族 | 重点领域 | 不应误用的规则 |
|---|---|---|
| C/C++ 开发 | C/C++、数据结构、构建、Debug、通用工程 | 不把 MCU 或 RTOS 当所有 C++ 岗位的必须项 |
| 嵌入式软件开发 | C、MCU、外设、RTOS（依 JD）、Debug | 不把 Linux 系统 IPC 当所有单片机岗位的必须项 |
| Linux 系统开发 | C、Linux、进程线程、IPC、I/O、网络、Debug | 不把 Linux pthread 与 RTOS Task 混为一谈 |

### 9.3 Gap 分类与优先判断

| 类型 | 条件 | 用户可理解的行动 |
|---|---|---|
| `evidence_gap` | 没有足够有效证据/待复核 | 先做小规模针对性验证 |
| `skill_deficit` | 有证据表明基础能力低于岗位最低要求 | 补基础并复测 |
| `depth_deficit` | 会用但岗位需要更深层机制 | 补原理、边界和复杂场景 |
| `practice_deficit` | 理论证据存在，但实践/排查不足 | 小型实践和故障处理 |
| `project_gap` | 技术能力与项目证明之间存在缺口 | 挖掘贡献或补可验证项目证据 |
| `expression_gap` | 经确认的事实简历没写清楚 | 结构化改写、事实补问 |
| `role_mismatch` | 多项必需条件与当前方向差距明显 | 提供补强或探索方向的选择 |

**V1.1 强制优先判断**：`assessed_level=null` 时先看 `performance_state`：`not_tested`/`insufficient_evidence` → `evidence_gap`；`demonstrated_below_L1`（独立有效基础证据交叉验证）→ 可形成基础 `skill_deficit`，但不做数值等级差；`disputed` → 待复核；`graded` 才可按岗位目标等级对照。`project_gap` 与 `expression_gap` 作为横向审查独立触发，不靠等级差自动触发。

### 9.4 用户报告中的岗位准备程度

V1 默认输出三种状态：`已验证达标 / 有证据的待加强 / 尚待验证`，分为 must、important、bonus。默认不输出“岗位匹配度 72%”式精确值；如之后采用百分比，必须公开算法、未知项比例和局限，绝不称为获面率或录用概率。

## 10. Career Coach 与成长计划闭环

### 10.1 三层结论不可混淆

- **技能事实层**：Rubric 和证据支持的等级，由 Assessment 更新。
- **岗位推断层**：RoleProfile 对照与差距，由 Gap Engine 计算。
- **行动建议层**：学习、项目、表达与暂缓建议，由 Career Coach 提出并经规则校验。

Career Coach 不能改写上游技能等级或替用户创造项目事实。

### 10.2 优先级策略

第一步先执行硬约束：must 优先、未验证先小成本验证、当前求职时间与资源约束、已有项目可利用时先挖掘、风险性概念错误优先复核。之后才按岗位收益、严重程度、紧迫性、学习成本、复用价值与用户偏好排序。

建议输出：首屏最多 **3 个“现在做”（P0）**；详细页可显示 P1/P2；“当前不建议重点投入（DEFER）”可显示 1–3 条，但不为凑数而强行生成。

### 10.3 DEFER 强制门槛

一条暂缓建议同时满足：目标岗位明确、该技术当前相关度可解释、存在更优先的可执行行动、不依赖编造招聘数据、说明仅限当前阶段、与当前 JD 的 must 不冲突。

**错误**：“Docker 没用，不要学。”  
**正确**：“对于当前 MCU 嵌入式实习目标，这份岗位要求并未将容器化列为关键项。先补中断与共享资源安全性的实践证据更有针对性；如转向 Linux 后端或遇到 Docker 必需的 JD，再调整优先级。”

### 10.4 每条计划的最小结构

| 字段 | 内容 |
|---|---|
| `action_id/type` | verify、learn、practice、project_enhance、resume_rewrite、explore_role、defer |
| `linked_gap_ids` | 对应哪条已发现的 Gap |
| `why_now` | 为什么现在做 |
| `objective` | 具体可观察目标 |
| `steps` | 2–5 步行动 |
| `deliverable` | 输出物：程序、分析记录、项目说明、简历文本等 |
| `acceptance_criteria` | 如何判断任务已完成 |
| `reassessment` | 如何通过其他题目/项目证据复测 |
| `priority/status` | 优先级、建议/接受/进行中/用户已标记/已验证 |
| `source_refs` | 评估、JD、项目事实等依据 |

### 10.5 计划执行与复测

`建议 → 用户接受 → 进行中 → 用户标记完成 → 发起专项复测 → 新增能力证据 → 生成新能力/Gap 快照`。

- “用户已做”不等于“验证通过”。
- 时间未知时给优先顺序，不强制虚构具体完成日期。
- 只剩较短求职窗口时，优先低成本验证和改进已知简历事实，而非强行安排大型项目。
- 用户改变岗位、计划或可投入时间，需重新计算建议并保留之前版本。

## 11. 核心数据实体、版本与系统边界

### 11.1 概念数据实体（不是最终数据库 DDL）

| 实体 | 主要关系 |
|---|---|
| `User / CandidateProfile` | 拥有简历、目标岗位、诊断、计划 |
| `ResumeFile / ResumeSnapshot` | 原文件 + 结构化字段 + 用户确认版本 |
| `Project / ProjectClaim` | 项目、本人贡献声明、技术及证据来源 |
| `Skill / Subskill / RubricVersion` | 稳定技能 ID 与等级标准 |
| `SkillClaim` | 简历/用户的声明，不直接授级 |
| `RoleProfile / JDSource` | 岗位画像、JD 来源和版本 |
| `AssessmentSession / Question / Answer` | 诊断过程、题目、回答与状态 |
| `AnswerEvaluation / Evidence / UserSkillState` | 单题评价、证据、能力快照 |
| `ResumeReview / ProjectReview` | 简历和项目分维度审查、改写建议 |
| `GapReportSnapshot / GapFinding` | 某版本能力和岗位对应的缺口 |
| `CoachAction / ImprovementPlan` | 可执行任务、状态与复测关联 |
| `AuditEvent / ConsentRecord` | 重要纠正、版本变更、数据用途与操作记录 |

### 11.2 核心数据不变量

1. `SkillClaim ≠ UserSkillState`。
2. `ResumeSnapshot`、`AssessmentSnapshot`、`RoleProfile`、`GapReportSnapshot` 必须有独立版本或不可变快照标识。
3. 更换 RoleProfile 后**只重算 Gap 和 Plan**；不静默修改既有能力历史。
4. 用户修正个人贡献，创建新的已确认事实版本并触发受影响报告重算，不抹掉审计记录。
5. `assessed_level=null` 不表示 0 分，也不参与简单数值相减。
6. 每份最终建议应能追溯到 Skill、JD/岗位模板、回答或项目事实。
7. 同一请求幂等，同一答案不得在重试中重复累积证据。
8. 跨域共用的一条回答可以绑定多个 Skill ID，但不能重复当成独立样本累加可信度。

### 11.3 服务/组件逻辑边界

```text
Web UI
 ├─ Identity / Profile Service
 ├─ Resume Parser + Resume Review
 ├─ Role/JD Analyzer
 ├─ Assessment Orchestrator
 │   ├─ Question Planner/Generator/Validator
 │   └─ Answer Evaluator + Skill State Evaluator
 ├─ Gap Engine
 ├─ Career Coach / Action Planner
 └─ Reporting / History / Privacy Controls

Shared: Rubric/Role Registry + Snapshot Store + Audit/Event Log
```

这是**逻辑划分**，不是要求采用微服务或每块一个大模型。具体编程语言、数据库和 Agent 框架在后续架构设计中选择。

### 11.4 关键接口（逻辑契约）

- `upload_and_parse_resume` → `ResumeSnapshotDraft`。
- `confirm_candidate_snapshot` → `CandidateSnapshot`。
- `analyze_role_or_jd` → `RoleProfileDraft`（可确认）。
- `start_assessment / plan_question / submit_answer / evaluate_answer / update_skill_state / pause / resume / complete`。
- `build_gap_report(candidate_snapshot_id, assessment_snapshot_id, role_profile_id, constraints_version, policy_version)`。
- `build_action_plan(gap_report_id, policy_version)`。
- `request_reassessment(action_id)` → 新诊断会话。
- `generate_resume_suggestion(resume_span_id, confirmed_fact_refs)` → 文字建议与来源。

最终 HTTP URL、消息队列、调用模式与结构化 Schema 由技术设计确定，不在 PRD 锁死。

## 12. 非功能需求：隐私、安全、质量与体验

### 12.1 隐私与信息安全

- 简历包含姓名、电话、邮箱、教育、实习、项目等个人信息；仅收集必要字段，并明确说明用途、保存时间、模型处理方式及可删除范围。
- 强制账户间访问隔离；传输/存储保护；最小权限；敏感日志脱敏，不将完整简历直接写入普通应用日志。
- 第三方模型处理涉及个人材料时，应在产品告知和技术架构中说明数据流向，评估相关服务合同与适用合规要求。
- 用户可以查看、修正、导出/删除自己允许操作的数据；实际留存策略需要合规评审。
- 不得在缺乏授权的情况下发布用户简历或把私人项目材料给其他用户查看。

### 12.2 AI 安全和技术正确性

- 简历、JD、网页招聘信息和用户回答均是**不可信输入**；其中的指令文本不得改变系统规则。
- AI 输出必须经过结构化 Schema 校验与服务端不变量校验；生成的 C/C++/Linux 题目要进行技术正确性审核。
- 对含糊、技术错误或存在关键上下文缺失的题目，必须作废而不是继续计分。
- 模型输出异常时使用受限重试或规则化兜底报告，不产生凭空判断。
- 不执行用户提交的代码、附件脚本或未知二进制文件；不把简历内容直接拼成可执行系统指令。

### 12.3 体验和可用性

- 关键长流程允许暂停、恢复、跳题、修改确认信息。
- 上传、解析、题目生成、报告生成需要独立反馈和错误恢复状态；具体性能目标待原型压测后制定。
- 长文本、代码块及 PDF/DOCX 结构化结果须兼容主要桌面浏览器；移动端至少可阅读与完成文字题。
- 不以“你的能力很差”等羞辱性措辞评价用户；不过度鼓励，不把 AI 推断写成确定事实。
- 用户提及无项目/无实习，不应遭到系统性惩罚；可通过应用题建立知识证据，但项目贡献保持待验证。

### 12.4 中国大陆上线合规清单（待专业审查）

包括个人信息处理告知、同意与撤回、数据存储与删除、第三方模型数据流、用户内容安全、适用的网站/服务备案及生成式 AI 相关合规要求。具体适用义务必须在部署主体、服务商、部署位置明确后核查，本 PRD 不代替法律意见。

## 13. 业务验收标准与端到端测试用例

### 13.1 关键业务验收（AT）

| ID | 给定条件 | 系统必须做到 |
|---|---|---|
| AT-01 | 用户上传可解析的 PDF/DOCX | 提取并展示技能、项目、经历及来源，允许确认 |
| AT-02 | 上传文档无法解析 | 明确提示并允许重传/手动补录，不虚构内容 |
| AT-03 | 简历不存在自我介绍 | 给出是否必要的上下文建议，不盲目扣技术分 |
| AT-04 | 可识别的排版问题 | 指出具体问题与位置；识别能力不足时标待复核 |
| AT-05 | 同名“智能小车”项目，个人贡献不同 | 项目报告按实际贡献与证据区分 |
| AT-06 | 用户否认“本人实现 CAN 通信” | 去掉未经验证的本人贡献结论并记录修改 |
| AT-07 | 简历声明“精通指针”，仅答对一题 | 不直接授予整体 L2/L3 |
| AT-08 | CL-04 生命周期问题出现关键误区 | 保留基础证据，标记局部缺口，允许追问/复测 |
| AT-09 | 用户跳过 Linux 问题 | 不将其自动判成 Linux 较弱 |
| AT-10 | 用户基础题回答短但正确 | 可以澄清，不因字数少而直接降级 |
| AT-11 | 动态题存在歧义或技术错误 | 作废、不计分、可重新发题 |
| AT-12 | 用户已有目标 JD | 保留原文映射和用户确认的 must/important 信息 |
| AT-13 | 用户没有 JD | 使用通用岗位模板并标明来源 |
| AT-14 | 用户没有目标岗位 | 只推荐首批岗位族；用户选择前不强推岗位 DEFER |
| AT-15 | must 技能尚未测评 | Gap 输出待验证，而不是“差 L2 两级” |
| AT-16 | must 技能已有效评估低于要求 | 输出明确差距、证据与补强方案 |
| AT-17 | 用户切换嵌入式 → Linux 岗 | 重算 Gap 与建议，历史技能状态不被改写 |
| AT-18 | JD 写明 Docker 为 must | 不自动输出“当前不建议学 Docker” |
| AT-19 | 学生近期就要投递且空闲时间很少 | 优先给短期可执行任务而非强制长期大项目 |
| AT-20 | 用户没有 MCU 硬件 | 有替代方案时提供替代，不强制购买设备 |
| AT-21 | 用户手动勾选学习完成 | 不自动升级 Skill Level；需复测证据 |
| AT-22 | 简历没有优化百分比数据 | 不编造“性能提升 40%” |
| AT-23 | 用户再次提交同一答案请求 | 不重复写入问答或证据 |
| AT-24 | 中途关闭诊断页面 | 恢复会话与题目状态，不丢已提交答案 |
| AT-25 | 不同账户访问对方报告 | 拒绝访问，不泄露数据 |
| AT-26 | JD/简历文本包含“忽略之前规则” | 只当作待分析文本，不更改模型行为契约 |
| AT-27 | 用户要求删除个人诊断数据 | 按明确的保留/删除规则执行并反馈结果 |
| AT-28 | 报告尝试输出“获面概率 88%” | 规则校验阻止该未经证实的表述 |
| AT-29 | 同一证据影响 C Debug 和工程 Debug | 可以双重引用，但不会伪增独立证据数 |
| AT-30 | 用户反对评分或暂缓建议 | 可以查看依据、补证据、复测或重新规划 |

### 13.2 核心演示数据集（上线前必须准备）

- 技能样例：`CL-04` 指针（基础/应用/生命周期误区）、`LNX-05` IPC、`RTS-01` 任务/调度、`ENG-03` 调试。
- 简历样例：完整简历、排版混乱、项目个人贡献模糊、无项目、扫描失败、内容包含假指令。
- 岗位样例：模板、正常具体 JD、含糊 JD、与模板冲突 JD、某项技术 must 的 JD。
- 用户行为：全部答对、基础薄弱、短答、跳过、中断、修改贡献、复测、切换岗位。

### 13.3 AI 质量门槛（先定测试方式，不伪造达标率）

- 至少由两名相关方向的技术评审独立标注代表样例，对关键等级判断、误区与 Gap 分类进行分歧复核。
- 统计“题目技术错误/歧义发生率、虚构事实事件、未验证误判为弱项的次数、关键技能错判、建议是否关联真实证据、同类样本结论一致性”等。
- 精确上线阈值应基于试运行样本确定；对虚构量化成果、跨账户数据访问等严重问题实施阻断式门槛。

## 14. 产品指标与实验验证计划

### 14.1 北极星方向（不等同于既有统计结论）

**有效诊断后行动率**：完成首次诊断的用户中，接受至少一项有明确验收标准的建议并开始执行的比例。该指标体现产品是否促成行动，但不证明获面率提升。

### 14.2 用户漏斗指标

| 环节 | 关键指标 |
|---|---|
| 访问/激活 | 开始诊断率 |
| 上传 | 简历上传成功率、解析成功率、人工确认率 |
| 岗位 | 目标岗位选择率、JD 确认率 |
| 诊断 | 诊断完成率、平均时长、跳题率、恢复率 |
| 报告 | 能力依据查看率、Gap 查看率、简历建议查看率 |
| 行动 | 计划接受率、任务启动率、用户标记完成率 |
| 复测 | 专项复测启动/完成率、复测后的证据覆盖变化 |
| 质量 | AI 错判申诉、题目作废、用户事实纠正、虚构事实事件 |

### 14.3 验证研究

1. **问题访谈**：让目标学生展示当前简历、项目说明、目标 JD，了解他们是否能读懂报告及哪些建议真正有用。
2. **可用性测试**：从首次进入到完成诊断，记录卡点、放弃原因、题量疲劳和页面误解。
3. **专家标注**：技术评审评价题目、关键误区、等级及行动建议，形成标注基线。
4. **建议有效性访谈**：用户能否基于报告制定接下来一周的行动；对于 DEFER 是否认可理由。
5. **后续反馈**：在获得合法授权和足量真实数据后，才研究投递/面试转化的关联；避免从少量自选样本推断因果。

## 15. 发布范围、依赖与上线门槛

### 15.1 本版 MVP 边界冻结建议

**必须覆盖的闭环**：上传/补录 → 简历解析/质量问题 → 技能和项目确认 → 目标岗位/JD → 能力诊断 → 可解释画像 → Gap → 计划与 DEFER → 真实简历文本建议 → 轻量复测。

**允许简化的深度**：岗位仅三个族；Rubric 先重点覆盖每域最核心节点；简历建议只输出可复制的文字；基础排版审查只评价有可靠解析依据的项目；计划先做简单任务状态；暂无课程平台、完整 WYSIWYG 编辑器。

### 15.2 依赖清单

| 依赖 | MVP 最小标准 |
|---|---|
| Rubric Registry | 稳定 Skill ID、可版本化、核心节点有经审校的题目蓝图 |
| Role Profile Registry | 3 个岗位族模板 + 能确认具体 JD 抽取 |
| Resume Parser | PDF/DOCX 基本结构化提取与可靠降级 |
| AI 调用层 | 受控出题/评价、Schema 校验、限次重试、日志脱敏 |
| Snapshot Store | 用户、简历、问答、证据、岗位、Gap、计划可关联和追溯 |
| 质量校验 | 题目歧义、评分依据、事实幻觉和关键规则的阻断机制 |
| 隐私控制 | 用户数据隔离、用途说明和删除流程 |

### 15.3 建议的上线前阻断问题

- 模型能否在标准样例下对关键技术错误给出稳定判断？
- 解析不准确时是否会诱导错误的能力推断？
- 是否仍存在“未验证即较弱”的误判？
- 是否会编造项目数字/个人贡献？
- 是否会生成技术错误的 C/C++ 等代码题并用于评分？
- 是否能防止越权获取其他用户简历及答案？
- 是否明确了用户数据的存储、第三方处理和删除规则？

若上述存在重大问题，先保持受限试点而不是宣称成熟产品上线。

## 19. V1.1 八项正式决策与跨文档统一实现要求

### 19.1 D-R8 最终产品级决策

**2026-10-08，产品负责人批准方案 A**：V0 用户技术问答提交后即时收到提交确认和人工复核状态。只有人工审核通过的同一内容版本才能查看正式技术等级、关键短板、项目个人贡献增强、局部 Gap 和 Career Coach 最终建议。未经批准的 AI 候选结果不向用户以正式结论展示。已有 D-R2 简历初评仍可在答题前显示，但不得伪装技能认证。

审核状态 `draft_ai → pending_human_review → (needs_revision / rejected / approved) → published`。`published` 必须有 `approved` 审核记录、`report_hash`、审核人和版本；涉及事实/等级/Gap 的改动需要重新审核。任何草稿 URL/API、对象存储直链都不得绕过服务端权限和状态。用户更正项目责任或撤回授权时撤销受影响旧版的可见性并触发必要的重审或删除。

**体验规则**：提交后展示“已收到你的回答，技术结论需经人工复核后开放”、当前状态和再次查看方式；不能给没有运营承诺依据的具体审核完成时刻。V0 可使用受控会话令牌查看审核状态，确保到期/撤销后不可访问；无需因此提前建设完整账号系统。人工无法完成审核时应提供“审核未完成／本次无法给出正式结论”及删除通道，不自动生成已审等级。

### 19.2 三套彼此独立的状态

| 字段 | 枚举 | 作用 |
|---|---|---|
| `assessment_status` | `not_started/in_progress/partial/sufficient/insufficient_evidence/needs_review` | 当前评估流程/证据充分性 |
| `performance_state` | `not_tested/insufficient_evidence/demonstrated_below_L1/graded/disputed` | 被观察到的能力证据性质 |
| `assessed_level` | `null/L1/L2/L3` | 已有足够证据支持的技能等级 |
| `review_status` | `draft_ai/pending_human_review/needs_revision/rejected/approved/published` | 人工审核与对外发布 |

以上状态属于不同实体/轴，不能当作单个扁平互斥状态集合。`demonstrated_below_L1` 必须通过多个不同且有效的 L1 基础验证及人工审核；仅答错一题或 L3 难题不成立。所有 `null` 不直接视为能力差；历史 L0 不进入新授级数据。旧 Agent 规范中 `assessed` 兼容映射 `sufficient`，不能让开发端同时输出两套写法。

### 19.3 覆盖率定义及对外约束（D-R4）

`coverage = sufficiently_evaluated_must_nodes / reviewed_must_evaluate_nodes`，仅在 `must_evaluate` 经人工审核、分母非零且关联当前岗位/版本时展示。“足够评估”包含 `graded` 和经交叉验证的 `demonstrated_below_L1`；`not_tested/insufficient_evidence/disputed` 不算。该覆盖率**不是能力水平分、达标率或获面概率**。分母无效时只列已测/待测，不伪造百分比。V0 总是局部报告；V1 的整体岗位准备度需额外通过专家批准的覆盖门槛和质量标准。

### 19.4 岗位模板与重要度（D-R7）

- 三个实习岗位原型按 JD 校准后发布。采样规划每原型 12～20 候选，争取至少 8 个独立、去重、可溯源且符合层级的有效 JD；该规模是研究假设，不代表统计充分性。
- 采集 JD 原文及 URL、抓取/发布日期（可知时）、企业、地区、实习层级、岗位职责、技术要点；去重时不能将同岗多次转载算多份独立数据。
- 从 JD 映射 Skill ID 后由专家分别确定 `must / important / bonus / not_required` 与 `must_evaluate`。未提及 ≠ `not_required`；岗位措辞如“精通”≠ 自动 L3。
- `RoleProfile` 每次发布保留来源 ID、样本范围、抽取/审校人员、批准时间、审校状态、版本和适用边界。未经审核的技能要求不能成为强制 Gap 或 DEFER 的唯一依据。
- 用户输入具体 JD，经抽取后须确认岗位事实；具体 JD 优先于通用模板，但仍须处理含糊、不可信或互相冲突的要求。

### 19.5 V0 发布闸门（D-R5、D-R6）

- **人工复核**：正式技能等级、关键短板、项目事实增强必须经过对应领域审核批准；审批和内容版本绑定。
- **技术验证**：题目有技术错误/未定义行为歧义时作废，不扣分；至少两名相关专家独立标注基准样本，分歧仲裁或标 disputed。
- **重大缺陷**：跨会话越权、虚构成果正式发布、错误题计分导致严重误判、未经批准公开报告等 S0/S1 均阻止相关输出上线，需修复、回归、授权恢复。
- **隐私**：受控短期会话、用途告知、脱敏最小化、访问隔离、用户删除、模型供应商训练与留存行为核验；试点前由实际运营和合规人员审核。
- **暂定留存**：原始简历解析并确认后尽可能删除；无活动 7 天过期、审核需要时最长 30 天只是待批准配置建议；备份/供应商/日志独立确定删除义务及可验证实现，不能冒充法定固定时长。
- **质量门槛**：60～90 个研究案例、两人独立标注等属于计划建议；试点前仍需确定实际样本量、度量、签署阈值、模型供应商、部署区域及发布负责人。设计通过 ≠ 真实质量验证通过。

### 19.6 可执行端到端验收（V11-01 ～ V11-17）

## 20. 评审结论与尚未关闭的准入项

**产品级结论**：D-R1～D-R8 已由产品负责人确认，允许进入 UI/UX 原型、系统架构和 V0 任务拆分。**不等于 V0 真实用户试点获得准入许可，也不表示真实 JD/专家模型已经校准完成。**

### 20.1 遗留执行事项清单（以独立文件为跟踪主表）

- 上线阻断：三岗位 JD 样本真实采集与人工复核；must_evaluate/角色模板批准；核心 Rubric 和题目有效性校验；专家标注样本与人工审核产能；QA 门槛签署；实际数据处理者、部署区域、供应商与合同审核；数据保留、删除 SLA、备份供应商核查；安全权限与数据删除回归。
- 实施前设计依赖：临时会话与待审报告查阅机制；报告审批版本及撤回；统一字段 schema 与已有规范修订；V0 题目预算、单次问答成本和可用性验证；PDF 解析可用性与文件安全阈值。
- 后续验证：V1 简历数值评分、总体岗位准备度、专项复测与深度诊断；更丰富的岗位模型、长期成长价值。未通过评审不得隐式开启。

### 20.2 正式修订原则

旧版 PRD 和配套规范为历史与设计参考，**涉及 V1.1 变更的开发实现以本文规定为准**。后续架构设计应输出单一版本化枚举与数据契约，旧规范需以兼容说明或后续修订同步，不能直接复制旧字段造成冲突。
